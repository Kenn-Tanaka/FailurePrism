# ADR-0007: 帰結以降の事後調査活動の自動除外と第二の帰結（レジリエンス・リカバリー）の保持

- **ステータス**: `Accepted`
- **決定日**: 2026-11-04
- **対象コンポーネント**: VTA UI (Control Panel) / LLM Service / Causal Slicing Engine / VTA Store
- **関連ドキュメント・コミット**: [ADR-0001: 2段階イベント分類と仮判定一括採用](file:///docs/adr/0001-two-stage-event-classification-and-batch-adoption.md), [ADR-0002: 受動客体における帰結ノード表示維持](file:///docs/adr/0002-outcome-node-card-preservation-for-passive-objects.md), [ADR-0004: 正規化処理の人間監査可能性](file:///docs/adr/0004-normalization-audit-and-human-traceability.md)

## 1. コンテキストと課題 (Context & Problem Statement)

航空事故、鉄道事故、医療事故、プラント障害などの公式事故調査報告書では、本文の後半部分に「事故調査委員会の発足・活動」「関係者への事情聴取」「行政指導・業務改善命令」「再発防止提言・組織体制見直し」といった事故発生後の手続きが詳細に記述されています。

これらをそのままバリエーションツリー分析（VTA）の入力として全件抽出・分析すると、以下の深刻な課題が発生していました：

1. **トークン消費の浪費と処理遅延**:
   - 事故そのものの経緯と直接関係のない膨大な事後手続き・調査活動の記述がLLMに送信・処理され、推論レイテンシとトークン消費を大きく圧迫する。
2. **事故因果分析の本質の埋没**:
   - 事故帰結（衝突、火災、設備損壊等）の後に「事故調査委員会」「国土交通省」などのレーンが新設され、ツリー最上部に居座ることで、事故分析の本質である「どの変動要因が事故を引き起こしたか」の可視化が損なわれる。
3. **レジリエンス行動（直後のリカバリー行動）の喪失リスク**:
   - 事後活動を排除しようとして「事故発生時刻以降のイベントを一律削除」する単純な時間カットを適用すると、事故直後に実施された緊急脱出退避（例：羽田空港衝突事故において乗客・乗員全員が無事脱出した行動）や延焼防止・二次災害防止措置といった、安全分析上極めて価値の高い**レジリエンス（回復力・二次被害防止行動）**まで削除されてしまう。

---

## 2. 決定理由の要因・制約 (Decision Drivers)

- **ユーザー主導のスコープ設定（デフォルト除外）**:
  - 一般的な事故原因分析のニーズに応えるため、「⚡ VTAツリー自動生成」ボタンの直上に、デフォルトでON（推奨バッジ付き）のチェックボックスUIを配置する。
  - 事後調査プロセスそのものを分析対象としたい利用者のために、チェックを外せば全事象を抽出できる柔軟性を保持する。
- **第二の帰結（Resilient / Recovery Outcome）の正当な保全**:
  - 事故による直接的な損失・被害を示す「第1の帰結（Loss Outcome）」だけでなく、直後のリカバリーや二次災害防止の成功（全員脱出成功、被害極小化など）を「**第二の帰結**」として正当に認識・抽出し、ツリー内に明示的に残す。
- **多層防御（プロンプトガードレール ＋ 決定論的因果スライシング）**:
  - LLMプロンプトの指示だけに依存せず、LLM出力後にグラフ理論に基づく決定論的な逆走因果トラバース（Causal Backward Slicing）を実行することで、事後調査などの非因果サブグラフを100%確実に除外する。
- **台帳整合性と監査可能性の維持 (Auditability)**:
  - 除外されたイベントは闇雲に消去せず、VTA台帳（`analysis.dispositions`）の `excluded` 行として「帰結以後の事後活動・調査活動として除外 (post-outcome-scope)」理由を記録し、人間が監査できるようにする。

## 3. 検討した選択肢 (Considered Options)

- **選択肢1: 時刻文字列による単純なタイムスタンプ比較カット**
  - *問題点*: 報告書内の時刻表現は「09:15ごろ」「直後」「翌日」「-（不明）」など非構造的であり、文字列比較によるカットオフは誤判定が頻発する。また、事故直後の脱出行動と翌日の調査委員会活動を時刻だけで安全に切り分けることが困難。
- **選択肢2: LLMのシステムプロンプト指示のみによる除外**
  - *問題点*: LLMのハルシネーションや指示の取りこぼしにより、事後調査のノードが数件残存するケースを完全には防げない。
- **選択肢3: 単一帰結ノードのみを起点とする厳格な逆走因果スライシング**
  - *問題点*: 事故衝突などの主帰結のみを起点とすると、主帰結の後に分岐した緊急脱出や救助・延焼防止などのレジリエンス行動（第2帰結）が「主帰結の原因ではない」として一括削除されてしまう。
- **選択肢4: プロンプトガードレール ＋ 複数帰結（損失＋リカバリー）対応の多層防御スライシング（採用）**
  - *利点*: LLMに事後調査活動の除外とリカバリー帰結の保持方針を与えつつ、生成後に第1帰結（損失）と第2帰結（リカバリー）の双方から逆走因果トラバースを実施。主事故の先行要因と直後のレジリエンス行動の双方を正しく残し、事後調査活動のみを確実に排除する。

---

## 4. 決定事項 (Decision Outcome)

以下のアーキテクチャを採用し実装しました：

```
                    【入力テキスト（事故調査報告書）】
                                   │
       ┌───────────────────────────┴───────────────────────────┐
       ▼ [スコープ除外 ON (既定)]                             ▼ [スコープ除外 OFF]
【POST_OUTCOME_SCOPE_POLICY 注入】                      【ベースプロンプトのまま】
 - 調査委員会・事情聴取等を [整理] excluded へ              - 全文をそのまま抽出
 - 二次災害防止・全員脱出等を「第二の帰結」として保持
       │                                                       │
       ▼                                                       ▼
【LLM 全文正規化・推論】                                【LLM 全文正規化・推論】
       │                                                       │
       ▼                                                       ▼
【決定論的因果スライシング (filterPostOutcomeScope)】              │
 - 第1帰結（損失）＋ 第2帰結（リカバリー）を特定               │
 - 帰結ノード群から因果DAGを逆走トラバース (Backward BFS)      │
 - 到達可能な因果連鎖・リカバリー連鎖のみをツリーに残す        │
 - 孤立した事後調査ノード・エッジ・空レーンを安全に除外        │
 - 除外イベントを analysis.dispositions (excluded) に記録      │
       │                                                       │
       └───────────────────────────┬───────────────────────────┘
                                   ▼
                    【完成したVTAツリー / 台帳】
```

### 主な実装仕様

1. **ストア設定 (`vtaStore.ts`)**:
   - `excludePostOutcomeActivities: boolean`（初期値: `true`）
   - `setExcludePostOutcomeActivities: (enabled: boolean) => void`
   - 設定値は `localStorage`（キー: `vta_exclude_post_outcome_activities`）に永続化。
2. **UIコントロール (`ScenarioInputSection.tsx`)**:
   - 「⚡ VTAツリー自動生成」ボタンの直上に、推奨バッジ付きのチェックボックスを配置：
     `[✓] 帰結以後の事象（調査・行政対応等）を自動除外する [推奨]`
3. **プロンプトガードレール (`eventPrompts.ts`, `client.ts`)**:
   - `POST_OUTCOME_SCOPE_POLICY` を定義。オプションが有効な場合のみ `extractEventDraft` 実行時に `fixedPrompts.normalization.systemPrompt` へ動的注入。
   - 事故調査委員会の活動、事情聴取、行政処分等の事後手続きは [イベント] ではなく [整理] の `excluded` 行として出力するよう指示。
   - 事故直後の緊急脱出、防護発報、延焼防止など被害拡大を食い止めたリカバリー行動は「第二の帰結」として保持・抽出するよう指示。
4. **決定論的因果スライシングフィルタ (`granularityScore.ts`)**:
   - `filterPostOutcomeScope(schema: VTASchema): VTASchema` を実装。
   - 帰結ノード（`analysis.outcome.eventIds` および `n.type === 'outcome'`）を全探索。
   - 帰結ノード群を起点として、すべての先行因果エッジ（sequential, causal, dependency, impact, transfer, mutual 等）を逆走トラバース。
   - 到達可能集合に含まれない事後ノード・事後エッジを除去し、所属ノードが0件となった事後組織レーン（例：「事故調査委員会」等）も安全にクリーンアップ。
   - 保持対象ノード・カード（`nextCards`）が参照するイベント群（`keptEventIds`）は、事後ノード側と共有されていた場合であっても確実に保持（`nextEvents`）し、孤立カード（イベント0件）の発生を防止。
   - 除外された事象は `analysis.dispositions` に `kind: 'excluded'`, `reason: '帰結以後の事後活動・調査活動として除外 (post-outcome-scope)'` として登録。
   - 帰結が未同定（`status !== 'identified'` かつ `outcome` ノードなし）の場合は、誤スライスを防ぐため無変換で全ノードを維持する安全ガードを配備。

## 5. 結果と影響 (Consequences)

### メリット
- **事故分析の焦点化**: 事故調査委員会の活動や行政処分等のノイズがVTA図に混入せず、発端から事故発生および直後の脱出に至る真の因果連鎖に集中できる。
- **レジリエンス分析の維持**: 羽田空港衝突事故のような事例において、衝突自体の原因連鎖と、直後の乗客全員脱出という成功要因の双方がVTAツリー内に正当に共存する。
- **安全性と非破壊性**: 帰結が未特定の場合や事後活動そのものを分析したい場合には、安全ガードやUIトグルにより一切のデータ欠落を生じさせない。
- **監査可能性**: 除外された事象は台帳の `dispositions` に記録され、監査画面から人間が理由を確認できる。

### トレードオフ・考慮事項
- 報告書において「事故調査の過程で初めて判明した事実（証言・データ）」が事後調査の文脈として書かれている場合、LLMがその事実自体を調査活動と混同して除外しないよう、プロンプトで「客観的事実・証言は保持し、調査委員会の活動手続きを除外する」旨を明確化している。
