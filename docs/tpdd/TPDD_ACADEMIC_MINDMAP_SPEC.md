# 思考展開図（TPDD: Thinking Process Decomposition Diagram）内部アーキテクチャ・開発系譜 学術発表用解説文書

本書は、システム要求工学・設計支援ワークベンチ **TPDD-Editor** について、学会・シンポジウム（日本人間工学会、情報処理学会、人工知能学会、日本信頼性学会等）での研究発表・技術解説を目的として作成された文書です。
Gemini Notebook / NotebookLM 等に投入して「マインドマップ」を生成する前段階として、論理的階層（大テーマ $\to$ 中項目 $\to$ 小項目 $\to$ キーワード）を明確に構造化しています。

## 1. 研究・開発の学術的背景と問題提起

### 1.1 システムズエンジニアリングにおける「要求展開の断絶」
- **背景**:
  - 現代の大規模・複雑化するシステム（自動車、航空宇宙、社会インフラ、医療機器）では、最上位の顧客要求・安全要求から、末端の具現化機構（ハードウェア・ソフトウェア・回路）に至るまでの論理的トレーサビリティが不可欠。
- **課題（断絶の発生）**:
  - 開発現場では「要求仕様書（Word/Excel）」と「設計図・CAD/SysML」が乖離しやすく、なぜその機構が採用されたのか、どの要求を満たすためのものかがブラックボックス化する。

### 1.2 思考展開図（TPDD）の定義と位置づけ
- **TPDD (Thinking Process Decomposition Diagram) とは**:
  - 抽象度の高い目的・要求（左端）から、機能、機構、具体的部品（右端）へと、左から右へ階段状・ピラミッド状に具体化を進める「思考の展開」を可視化するダイアグラム。
- **既存手法（SysML, QFD, FAST等）との差別化**:
  - SysMLの厳格すぎるメタモデルによる認知的過負荷を排し、設計者の自由な発想（直感的なドラッグ＆ドロップ、独自設計体系の定義）と論理的構造（階層分解と依存線）を両立。

### 1.3 LLMを設計支援に直接適用した際の三大課題
1. **ハルシネーション（虚偽生成）**:
   - 存在しない規格や物理的に不可能な数値をさも正しいかのように出力する。
2. **文脈の乖離（Lost Context）**:
   - 単に「ブレーキの機構案を出して」と問うと、それが新幹線用なのか自転車用なのかを忘れ、的外れな提案を行う。
3. **設計図の非可逆的破壊**:
   - AIに図面データ（JSON/XML）を直接書き換えさせると、ユーザーが配置したレイアウトや既存の接続関係が壊される。

## 2. コア設計思想とパラダイム

### 2.1 演繹的・前方展開アプローチ（Deductive Forward Synthesis）
- **目的から手段への展開**:
  - 「$A$ を達成するために $B_1, B_2$ を具現化する」という演繹的論理展開。
- **後方分析ツール（VTA）との対照性**:
  - 過去の事故調査から学ぶ帰納的アプローチ（VTA）に対し、TPDDは未来の安全なシステムを計画する前方展開アプローチであり、FailurePrismにおけるコインの表裏を成す。

### 2.2 人間中心協調設計（Human-in-the-Loop: HitL と決定論的防壁）
- **AIは「提案者」、人間は「決定者」**:
  - AIが勝手に図面を更新することは絶対に許可しない。
  - AIの提案は「候補カード」としてサイドパネルに提示され、設計者が吟味・選択して「採用」をクリックした時のみ、プログラムが決定論的にノードとエッジを生成・配置する。
- **1手でのUndo/Redo**:
  - AIが生成した複数ノード・エッジの追加も、完全に1コミットの履歴として管理され、即座に元に戻せる。

### 2.3 階層的詳細化と認知的抽象化（サブ図への潜り込み）
- **クモの巣化（認知的パンク）の防止**:
  - 1枚のキャンバスに数百ノードを平面的に並べると人間には把握不能になる。
- **サブ図（詳細図: Detail Diagram）アーキテクチャ**:
  - 任意のノードに下位図面を紐付け、ダブルクリックで潜り込める（例：「エンジン制御」ノードの中に、独自の要求 $\to$ 機能 $\to$ 機構の図面を内包）。
  - 何階層でも掘り下げ可能で、大規模複雑システムの分割統治を実現。

## 3. 内部アーキテクチャと中核技術要素

### 3.1 独立直交データモデル（種別 `kindId` と 列 `levelId` の直交分離）
- **概念の分離**:
  - **ノード種別 (`nodeKinds`)**: 「それが何であるか（要求、機能、機構、制約、リスク等）」。Paul Tol Lightカラーパレットによる色分け。
  - **抽象度列 (`levels`)**: 「設計プロセスのどの段階か（要求定義、基本設計、詳細設計等）」。左から右への水平配置レーン。
- **完全直交性**:
  - ノード種別と列が1対1に固定されておらず、「機能列の中に一時的に置かれた未解決要求」など、柔軟な思考過程を表現可能。
  - 分野別プリセット（機械設計、ソフトウェア設計、電子回路設計、カスタム）を標準搭載。

### 3.2 4種類のエッジセマンティクス
1. **分解（`decomposition`）**: 親ノードの目的を達成するために子ノードへ細分化する主矢印（実線）。
2. **依存（`dependency`）**: 「機能Aが作動するには機構Bの電力が必要」といった機能間・機構間の横断的依存（破線）。
3. **制約（`constraint`）**: 「コスト1万円以下」「重量5kg以下」等の要求が下位機構を拘束する関係。
4. **参考・代替（`reference`）**: 「別の案として機構Cも考えられる」という設計代替案の紐付け。

### 3.3 堅牢な状態管理と不変性保証
- **技術スタック**:
  - React 18, TypeScript (Strict Mode), Vite, Tailwind CSS, Lucide Icons.
- **`useReducer` + Context アーキテクチャ**:
  - 永続化対象の `Project` ドメインモデルと、選択状態やパン・ズームなどの一時的UI状態を厳格に分離。
  - 50件の深さを持つ不変履歴（Undo/Redoスタック）。
- **Zod による Schema v2 検証**:
  - ファイル保存時・読込時・IndexedDB自動保存（1秒debounce、最大10世代復元）において、スキーマ構造および参照整合性（存在しない `kindId` や `levelId` の参照、自己ループ線の排除）を厳密に保証。

### 3.4 ネイティブベクターSVG直接描画エンジン
- **描画品質と外部連携**:
  - サードパーティのキャンバスライブラリに依存せず、自前のSVGレンダラーにより描画。
  - Microsoft Word や PowerPoint、LaTeX に直接貼り付けてもフォント崩れやピンボケを起こさない純粋SVG 1.1規格出力。
- **視覚的認知工学**:
  - 色覚多様性に配慮した **Paul Tol Light** カラーパレットを採用。
  - 全角・半角文字幅を考慮した自動改行アルゴリズムにより、固定ノード幅内で美しいタイポグラフィを維持。

## 4. AI連携アーキテクチャと開発過程の進化系譜

### 4.1 決定論的境界契約（永続ID隠蔽とアプリ側配置決定）
- **ID露出の禁止**:
  - システム内部のUUIDはLLMに一切見せない。リクエスト内限定の局所参照番号（`K1`（種別1）、`N1`（ノード1））に変換して送信。
- **エッジ生成のアプリ側統御**:
  - LLMには接続線（エッジ）を作らせず、提案テキストと種別参照（`kindRef`）のみを出力させる。
  - 展開案（`expand`）なら `focus ➔ candidate` の `decomposition` エッジ、代替案（`alternatives`）なら `focus ➔ candidate` の `reference` エッジをアプリが決定論的に結線。
- **未知種別の自己治癒**:
  - LLMが存在しない `kindRef` を返しても応答全体を破棄せず、UI上で「種別未設定」として人間が手動選択して救出可能。

### 4.2 祖先系譜（`ancestry`）の自動追跡（ADR-0019）
- **開発時の課題**:
  - 2階層以上深いサブ図のノードを展開する際、1-hop近傍の情報だけでは最上位の設計目的が失われ、AIが見当違いな提案を行う（例: 宇宙探査機のアンテナなのに家庭用WiFiルーターの機構を提案）。
- **解決策**:
  - `collectAncestry` により、現在のノードから親図・祖先図を最大5階層まで決定論的に遡り、最上位要求に至る「想いの系譜（`A1: 最上位要求`, `A2: サブシステム要求`...）」をプロンプトの `<DATA>` に文脈として注入。
  - AIが設計全体の意図から外れず、極めて的確な展開案・代替案を生成することに成功。

### 4.3 ノード状態認識（`status`）と却下案の汚染防止（ADR-0019）
- **開発時の課題**:
  - 設計者が検討の末に「却下（`rejected`）」としたノードの存在をAIが認識できず、却下した機構を前提に下位展開を提案したり、図レビューで矛盾として誤指摘する問題が発生。
- **解決策**:
  - ノード属性に `status`（`adopted` / `candidate` / `rejected`）とタグ（`tags`）を導入。
  - LLMプロンプトに却下ノードの取り扱い規約を明記し、却下された設計案の汚染を防止。

### 4.4 厳格な根拠検証を伴う要求レポート自動生成
- **機能概要**:
  - 作成されたTPDD図から、設計要求仕様書（Markdownレポート）をワンクリックで自動ドラフト生成。
- **事実性検証プログラム（`validateRequirementReportResponse`）**:
  - AIの勝手な作文・幻覚を完全に排除するため、文（statement）ごとに厳密な根拠引用（citation）を義務付け：
    - `requirement` 節: 起点ノードの引用必須。
    - `breakdown` 節 / `realization` 節: 分解エッジの引用必須。
    - `concretization` 節: 詳細図（サブ図）に実在するノードの引用必須（ADR-0019）。
  - 実在する図面要素を引用していない文はプログラムが警告付きで自動削除（除外）。

### 4.5 共通LLM通信基盤（ADR-0018）
- **SSE（Server-Sent Events）ストリーミング**: 1文字・1行ずつの逐次受信により、思考中のユーザーの不安を解消。
- **指数バックオフ自動再試行**: 一時的なネットワーク寸断やサーバー混雑（HTTP 429/502/503/504）に対し、最大3回まで自動待機・再接続。
- **機密保持**: APIトークンはメモリ一時保持のみとし、プロジェクトファイルやローカルストレージには一切書き込まない。

## 5. 学会発表での訴求ポイントと工学的貢献

### 5.1 自由度と厳密性の両立（ユーザー定義設計体系 × Zod構造検証）
- 形式的仕様記述（形式手法）の「堅苦しさ」と、自由記述マインドマップの「曖昧さ・崩れやすさ」というトレードオフを解消。
- 設計者の思考の自由を奪わずに、背後でZod・不変性管理・決定論的エッジ生成が働き、破綻のない要求系譜モデルを維持。

### 5.2 「AIに図面を描かせず、アイデアだけを借りて人間が統御する」新協調パラダイム
- 生成AIを自律的エージェントとして放任するのではなく、「コンテキスト（祖先系譜）を周到に整えて耳打ちし、アイデアの選択・配置・結線は決定論的プログラムと人間が統御する」というアーキテクチャの有効性を実証。
- ハルシネーションの危険を極小化し、ミッションクリティカルな安全設計分野でも実用に耐えうる生成AI協調開発環境の標準モデルを提示。
