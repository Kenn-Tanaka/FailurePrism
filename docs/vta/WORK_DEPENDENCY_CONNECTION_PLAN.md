## 1. 接続規則

異なるレーンの時系列上隣接するイベントについて、後の作業が前の作業の成果物・完了・判断結果・状態を前提としている場合、作業依存関係を提案する。依存関係の判断は原文に基づきLLMが行い、利用者が確認して採用する。時刻の近さ・同一用語・一般的な業務知識だけで依存を生成しない。

例：「旧仕様の総合試験手順書を作成した」「その手順書を使って結線した」は、手順書作成から結線作業への作業依存とする。単に「手順書を作成した」「別部署が作業した」という記述だけでは確定しない。

### 隣接の定義

- 接続候補となる2レーンのイベントを一つの時系列に並べ、間にその2レーンの別イベントがない組を対象とする。第三のレーンの無関係なイベントだけで候補から外さない。
- 基準は確定済みのイベント順序であり、画面上の上下位置やドラッグ位置ではない。
- 明示された前後関係を優先し、順序が決まらないイベントはLLMが原文の記述順を踏まえて出力した台帳順（sourceOrder）を使う。現行sourceOrderは原文の文字位置ではなく、イベント表の行順である。原文の時刻・記述順の解釈はLLMが担い、正規化時に必要なbefore関係を明示させる。アプリ側で自由記述時刻を再解釈しない。入力順を守れているかは原文付きの品質評価で確認する。
- 同じイベントIDを参照する複数カードは同じ発生として扱い、イベント自身への作業依存は作らない。
- レーン非表示・カード整理・提案対象の絞り込みで中間イベントを飛ばさない。隣接判定は正規データ全体で行い、その後に表示対象・指定範囲で候補を絞る。接続点表示のノードも中間イベントとして数える。
- 現行の共有カードで明示された順序未確定グループを無理に直列化しない。グループを縮約した順序で、他イベントが間に入り得る曖昧な組は自動提案せず要確認とする。時刻文字列の一致だけで同時発生グループを新設しない。現行モデルには一般的な同時発生グループ属性がないため、その完全な表現は今回の保証範囲に含めない。

初期実装では、この定義による隣接イベントだけを作業依存の自動提案対象とする。隣接しない依存の自動提案は範囲外とし、必要なら既存の手動編集で扱えるようにする。

## 2. データと表示

関係種別 `dependency` を追加し、sourceを前提作業、targetを依存作業として保存する。`before` は前後関係だけを意味するため、依存をbeforeへ置き換えない。

| 項目 | 設計 |
| --- | --- |
| 関係 | kind/meaning/categoryにdependencyを追加 |
| 端点 | 別イベントID・別主体ID・両イベントに対応する既存カードを必須とする |
| 向き | 前提作業 → 依存作業の一方向 |
| 描画 | 「作業依存」ラベルと一点鎖線を用い、画面・候補プレビュー・SVGで統一する。色だけに依存しない |
| 根拠 | 両端の原文参照と、何が何の前提かを示す理由を保存する |
| リソース・受領 | リソースなし、受領確認na。TSVではリソースを - とする |
| 実施状態 | 依存関係そのものには実施状態を持たせず、TSVは - とする。イベントの未実施と依存の存在を混同しない |
| 由来 | 既存の提案ID・LLM理由・採用理由・由来を引き継ぐ |

同じ端点に根拠のあるリソース移動等の線が既にある場合、依存線を機械的に重ねて増やさない。既存関係との対応を確認事項として示し、手動線・BREAK・意味の異なる線を上書きしない。依存線の削除・手動編集も安定した線IDで扱う。

LLMの提案IDは応答内だけの識別子とする。採用時にはアプリ側で衝突しない関係IDを一度だけ発行し、元の提案IDは来歴に残す。再投影・保存・Undo/Redoではその関係IDを維持する。同じ提案IDが別の応答で再使用されても衝突させない。

削除済み依存の再提案は、線IDだけでなく、方向付きのイベント・主体端点とdependency種別からなる意味キーでも検出する。再実行による別IDへの置換で削除指定を回避しない。必要な削除キーの保存属性は任意項目として追加し、既存ファイルにない場合は空として扱う。既存データで根拠を復元できない削除履歴の意味キーを推測して補完しない。

未実施の作業が前提に含まれていても、そのことだけで依存関係を否定しない。例えば、仕様変更の反映を前提とする試験に旧版手順を使った場合、未実施の事実はイベント側に残す。依存線からリソースの送受信や作業完了を推定しない。

## 3. LLM処理

### 入力と候補

1. 原文・確定イベント・主体割当・既存関係を開始時点で固定する。
2. 共通のイベント順序から、各レーン対について隣接する別レーンイベントの組を求める。全カード対を列挙せず、レーン対ごとのマージ走査で候補を作る。
3. LLMへ候補のイベントID・主体ID、前後関係、本文、参照原文を渡し、「後の作業が前の作業に依存しているか」を点検させる。
4. 既存のtransfer/impact/mutual/commonの提案も継続する。隣接制限はdependencyに適用する。
5. 原文が足りなければ要確認とし、新しい主体・イベント・根拠を創作しない。

依存が複数段落にまたがる場合に対応するため、両イベントの参照段落を重複排除して送り、必要な短い前後文脈も上限内で追加する。追加段落のIDを入力と確認画面に示し、送信していない段落を根拠にした応答は受け付けない。原文は引き続きanalysis.sourcesの固定スナップショットを使う。

候補数・原文文字数の上限を設け、超過時は件数を示して利用者に範囲を絞ってもらう。候補を黙って切り捨てない。

### 出力と修復

- 接続提案TSVは既存の13列を維持し、種類にdependencyを追加する。dependencyはaddのみ。共通イベント線を作業依存へrefineしない。
- 正規化台帳の関係表にもdependencyを追加し、新規抽出時にも同じ根拠・隣接条件を使う。まずイベント・主体割当・共有カード・dependency以外の前後関係を確定し、今回受信したdependencyをすべて除いた順序で候補を一括検証する。修復したdependencyで候補自身の順序を作らない。隣接しない候補や矛盾した候補は行単位の修復・要確認に回し、正常なイベントを再抽出しない。
- 初回抽出の関係表は既存10列を維持するため、接続提案の13列にある専用の理由欄はない。初回抽出では原文参照と両端イベントの説明を確認画面に示し、存在しない提案理由・採用理由を補完しない。専用の理由を持つAI接続提案と手動編集ではその理由を保存する。
- 接続提案画面では初期未選択とし、原文と理由の確認後に採用する。
- 形式・ID・根拠・隣接条件に不備がある行だけ限定修復する。根拠が不足する場合は同じIDの要確認へ移せる。正常行を再生成せず、修復が進まなければ停止する。
- 外部prompts.jsonと組込プロンプトを同時に更新し、一致をテストする。

## 4. 検証と適用

### 隣接・参照

提案生成と適用直前に同じ隣接判定を使う。依存の端点が表示範囲内の別レーンの既存カードであり、確定済みの正規データ上で隣接することを確認する。提案自身を使って順序を並べ替え、隣接条件を満たしたことにはしない。

表示対象判定はvisibleSchemaと同じ規則を共通化して使う。レーンを明示的にshowにした場合は、整理対象カードも表示される現行挙動を尊重する。候補の失効判定には、表示カードだけでなく全カードのイベント対応・共有カード構成も含める。非表示の中間カードの編集も候補に影響する。

隣接制限は初回自動抽出とAI提案の採用に適用する。保存読込、再投影、手動編集には一律に適用しない。採用後に中間イベントが追加されても既存線を自動削除せず、必要なら利用者へ再確認を促す。手動作成した非隣接の依存も読み込めるようにする。

候補の意味的妥当性はLLMと利用者が確認する。アプリは時系列・ID・原文参照・型・更新対象の整合性を検証し、依存が実在すると機械的に断定しない。

### 循環と重複

現行の接続提案は主体IDを頂点にして伝達の循環を検査している。この方式では、先の作業でA→B、後の作業でB→Aとなる正常な経過を拒否するため、イベント発生単位の検査へ改める。

- 前後を規定するbefore・dependencyと、実施されたtransfer/impactをイベントIDで結ぶ。同一イベントの主体間関係と相互確認は時間順の辺として扱わない。
- 既存関係と選択候補全体を組み合わせて循環を検出する。既存図に循環がある場合は候補の問題と区別して通知する。
- 表示上まとめたイベントを同じ高さに保つ制約との矛盾も検査する。矛盾したカードを自動で分割しない。
- 依存の重複は、種類と方向を持つイベント・主体の組で判定する。同じカードを参照していてもイベントIDが違えば無条件には同一視しない。
- 対称関係common/mutualの重複キーは、イベントIDと主体IDのペアを保って端点ペア同士を並べ替える。4つのIDを独立にソートしない。dependencyは方向を保持する。
- 同じ端点の別種別の関係、手動線、削除済み関係、BREAKとの競合を通知し、自動上書きしない。

採用した関係から描画を再生成し、保存・下書き・Undo/Redo・レポートの最新性判定へ一括反映する。手動配置は保持し、縦方向の再配置は利用者がBT自動整列を実行した時に行う。dependencyを新規提案して採用するまで、保存済み図に線を無断追加しない。

## 6. 受入条件

1. 手順書作成→その手順書を使う作業、前工程完了→後工程開始を、原文付きのdependencyとして提案できる。
2. 時系列上隣接するだけの無関係な作業、一般知識だけから推測した依存は要確認または候補なしとなる。
3. 中間イベントがある組、同一イベント、同一主体、未割当主体、範囲外の根拠を拒否する。
4. 第三レーンの無関係なイベントでは候補が消えず、対象2レーンの非表示・整理済み・接続点の中間イベントは飛び越えない。
5. 時刻不明でも明示的前後関係と入力順を用い、カード移動・コンパクト表示・列順変更で候補の隣接性が変わらない。
6. Aの先行イベント→Bの中間イベント→Aの後続イベントを許可し、同じイベント発生へ戻る循環は拒否する。
7. 候補編集後・一括選択後にも隣接、循環、カードグループの矛盾、重複、手動線・BREAKとの競合を再検証する。
8. 保存読込、下書き復元、Undo/Redo、再投影、BT自動整列、画面・SVG・レポートでdependencyの意味・方向・理由・参照を維持する。
9. 未実施イベントを含む依存が、リソース未送信や受領確認へ誤変換されない。
10. モック試験で転送契約・限定修復・採用を確認し、実LLMの意味判断品質は別に評価する。
11. 初回抽出のdependencyを除いた順序で隣接を判定し、非隣接候補の修復でも正常なイベントと主体を保持する。
12. 2回の提案が同じ提案IDを返しても、異なる関係を採用・保存・再読込できる。削除済み依存を別IDの提案が無断で復活させない。
13. 明示showによるカード復元を候補に反映し、非表示カードのグループ変更では既存候補を失効させる。
14. 手動の非隣接依存と、採用後に中間イベントが追加された依存を、保存読込・再投影で消さない。
15. 現行の全文正規化方式を共通入口から実行し、抽出・確認・反映・部分再抽出・変動判定の現行操作を維持する。方式導入だけを理由にLLM呼出し回数を増やさない。
16. テスト専用の別方式を登録して、共通検証・確認・採用まで通せることを確認する。本番UIに未実装方式を表示しない。
17. 方式・方式版・プロンプト・入力・モデルが異なる実行間で修復キャッシュを共有せず、中断済み／旧実行の結果が新しい下書きや別プロジェクトを上書きしない。
18. 生成方式の来歴がない既存5.0データと、未搭載方式の来歴を持つ構造上有効なデータを表示・編集・保存できる。方式固有の再実行は別途可否を判定する。

実装完了時にnpm run typecheckとnpm testを実行する。start-all.bat用のdistと配布ZIPを更新する際は、build.batをテスト省略なしで実行する。

## 7. 計画の自己レビュー（2026-10-29）

結論：方針は維持するが、以下の不足を修正してから実装する。本レビューで計画本文へ反映済み。

| 重要度 | 発見事項 | 修正方針 |
| --- | --- | --- |
| 高 | sourceOrderを原文位置とみなしていた。実際はLLMのイベント表出力順 | 順序の意味を訂正し、LLMの原文順保持を品質評価対象にする |
| 高 | 初回正規化では依存と順序を同時に生成するため、自己正当化した隣接判定になり得る | 今回の依存候補をすべて除いた順序を固定し、行単位で検証・修復する |
| 高 | 保存読込にも隣接制限を掛けると、手動線や後日編集した図を拒否する | 自動生成・採用時の条件と、保存データの構造検証を分離する |
| 高 | 現行のproposal:提案IDは再実行時に衝突する。削除指定も線IDだけでは再生成で回避される | 永続関係IDと応答内提案IDを分離し、削除した依存の意味キーを保持する |
| 中 | 表示判定が明示showと一致せず、隠れたカードのグループ変更を失効判定で見落とす | 表示規則を共通化し、全カード構成をスナップショットに含める |
| 中 | 同時発生の一般属性や初回抽出の専用理由欄が現行契約にない | 保証範囲を明記し、時刻文字列からの推測や存在しない理由の補完をしない |
| 中 | 描画用の循環回避を検証に流用すると、不正関係を見落とす | 順序計算の診断情報を共有し、描画継続と候補保留を分ける |

維持する設計上の判断：

- 主体単位の循環検査が正常な工程を拒否する問題を実装対象に含めた。
- 隣接の基準を明示し、非表示・範囲選択・座標操作による飛び越しを防ぐ。
- 提案を使って提案自身の隣接性を作る循環した判定を避ける。
- 依存関係の存在と各作業の実施状態を分け、未実施属性によって矢印が消える既存の分岐も修正対象とした。
- 同じ成果物を参照しているだけで、すべての作業間を密結合させない。
- 保存・描画だけでなく、初回抽出・修復・編集・レポートまで新種別の伝播を確認する。

2レーンを統合した隣接判定は、無関係な第三レーンのイベントによる候補脱落を避けるための設計判断である。ただし、実際には依存していても、その2レーンの中間イベントがある依存は初期の自動提案対象外となる。この制約を説明画面・利用手順に明示する。

自己レビューでは計画書のみを更新した。コード・プロンプト・配布成果物の変更、実装テスト、実LLMによる品質評価は実施していない。

## 8. 複数のVTA図生成スキームへの準備（追加計画）

自己レビューの採用に加え、将来複数の生成方式を装備するための準備を今回の実装範囲に含める。生成スキームとは、原文からイベント・主体・割当・関係を生成する処理方式を指す。LLMのモデル選択や図の配置方式とは別の設定として扱う。

### 今回整える境界

現行方式を「全文正規化・TSV台帳方式」として登録し、識別子は `fulltext-ledger` とする。実際に選べる本番方式は今回はこれ1つとする。将来、段階抽出方式などを追加する際、UI・保存・図描画を複製せずに追加できる構成にする。

処理経路は次のように分ける。

`入力・実行条件の固定 → 方式の実行 → 共通データの検証 → カード整理 → 接続・図への投影 → 利用者の確認 → 一括反映`

| 境界 | 担当する内容 |
| --- | --- |
| 方式固有 | LLMへの指示、呼出し段階、応答形式の解析、限定修復、正規イベント・主体・割当・関係への変換 |
| 共通の実行管理 | 実行ID、入力・プロンプト・設定の固定、キャンセル、進捗・ログ、結果の失効、方式別キャッシュの分離 |
| 共通の整合性検証 | ID・原文参照・端点・属性・循環・重複。今回の依存候補については承認済みの隣接制限も適用 |
| 共通の編集・表示 | カード整理、接続の投影、確認画面、採用、Undo/Redo、保存、SVG、レポート |

TSVは現行方式のLLM通信形式とし、方式間の内部契約には既存の型付き正規データ `VTAAnalysisData` を使う。これはLLMにJSON出力を要求する変更ではない。各方式は共通の原文IDを参照し、sourceOrderを「その方式が出力した基準順序」として提供する。根拠・時刻・本文を決定論的に推測して補完する処理は追加しない。

### 最小の方式契約

新設する `services/generation/` 配下に、契約、静的な登録表、実行サービス、現行方式のアダプターを置く。具体的なファイル分割は実装時に既存依存関係に合わせる。

- 方式の定義：`id`、方式の`version`、名称・説明、対応する共通データ版、部分再抽出などの対応操作。
- 入力：変更不可の原文スナップショット、実行ID、実行開始時のモデル・プロンプト・方式設定、必要に応じて対象範囲と既存分析のスナップショット。
- 実行環境：LLM通信関数、AbortSignal、進捗・ログ通知関数。方式からReactコンポーネントやストアを書き換えない。認証情報は通信層で扱い、方式の来歴には含めない。
- 出力：正規分析データ、警告・要確認事項、生成来歴。描画用ノード座標や採用済みストアを返す契約にはしない。

現行の `extractEventDraft` は共通実行サービスを呼ぶ互換入口として残し、既存呼出元を段階的に移す。`client.ts` 内の正規化・修復と、ストアからのプロンプト取得・進捗更新を分離する。処理の都度グローバル設定を読むのではなく、開始時に固定した設定を修復まで使う。外部prompts.jsonの現行キーはアダプターで受け取り、既存のカスタムプロンプトを失わせない。

方式は共通データに変換した結果を返すが、検証に合格したと自己申告するだけでは採用しない。共通実行サービスで参照・構造を再検証し、現在の確認画面を経由して反映する。進捗の段数は方式が通知できるようにし、UIに現行の3段階を固定しない。

### 関連操作と生成方式の関係

- 「レーン間接続をAIに提案」は、生成済みの共通分析データを入力にする独立サービスとする。元の生成方式が違っても、同じ接続条件・根拠検証・利用者による採用を適用する。
- 今回の2レーン間の隣接条件は承認済みの共通ルールとして維持する。方式の違いを理由に無効化しない。将来このルール自体を変える場合は、明示的な接続方針とその版を別途設計する。
- 「背景・除外・要確認からの部分再抽出」は方式の対応操作として定義する。現行方式の実装を移し、未対応方式ではその操作だけを無効化して理由を表示する。別方式へ黙って切り替えない。
- 部分再抽出の結果は、アプリ側でIDを重複なく割り当てて既存分析へ統合する。統合後の全イベント順序で新しい依存候補を再検証し、抽出部分内だけの隣接判定で採用しない。
- 変動要因の判定は現行どおりイベント確認後の独立操作とし、全方式に必須の抽出段階として埋め込まない。

### 来歴・再開・既存データ

生成来歴を任意属性として保持する。最低限、実行ID、方式ID・版、適用した接続ルール版、モデルID、実効プロンプトの指紋、入力の指紋を記録する。共通スキーマの版、方式の版、プロンプトの版を混同しない。APIキー等の認証情報は保存しない。来歴は調査用であり、LLM出力の完全な再現を保証するものではない。

全体生成の来歴は分析データに、後から採用した接続の来歴はその関係に紐付ける。部分再抽出の実行来歴も識別できるようにし、一部を再生成しただけで図全体を最新方式で生成したと記録しない。通常の手動編集・保存で来歴を失わせない。

修復キャッシュは少なくとも、プロジェクト、方式ID・版、操作種別、入力・対象範囲、実効プロンプト、通信先・モデル、結果に影響する設定で分離する。方式内部の途中TSVは内部状態として保持し、共通保存形式には要求しない。処理開始時の実行IDと入力スナップショットを結果受領時・採用時に照合し、遅れて届いた応答を採用しない。

既存5.0データで来歴がない場合は「生成方式不明」として読み込む。現行方式で生成したと推測して補完しない。未搭載の方式IDでも共通データの構造が有効なら図を表示・編集できる。元方式が必要な再実行のみ不可とし、既存データの表示に方式の実行コードを要求しない。来歴不明の既存図で部分再抽出する場合は、現行方式を使うことを操作画面に明示する。旧形式の変換機能は追加しない。

### 今回と将来の範囲

今回実装するのは、現行方式1つの登録、共通入口、共通データ契約、実行・キャッシュの分離、来歴、関連操作の分離、および契約テストである。第2の方式はテスト専用の簡単な実装で差し替え可能性を確認する。

本番用の第2方式、方式選択UI、複数方式の並列生成・比較・結果統合、自動的な方式切替、外部プラグイン読込、汎用ワークフローエンジンは将来の実装とする。方式を追加するためだけに、新しい依存パッケージやLLM呼出しを増やさない。

### 追加計画の自己点検

- 共通データへ出力する方式契約により、TSV台帳を将来のすべての方式へ強制しない。
- LLMによる意味判断を方式側に置き、共通処理は検証・管理・表示を担う。承認済みの接続ルールを方式別の裏口で回避しない。
- 抽出だけでなく、部分再抽出・接続提案・変動判定にも境界を設け、現行方式への隠れた依存を残さない。
- 登録表とアダプターに留め、方式が1つの段階で不要な選択UIや複雑な拡張機構を作らない。
- 方式の変更と既存図の置換を分離し、生成結果は確認待ちにする。保存ファイルを開いたことを契機に再生成しない。

この追加も実装計画への反映であり、コード・プロンプト・配布成果物はまだ変更していない。
