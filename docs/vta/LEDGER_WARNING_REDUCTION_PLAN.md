## 2. コード照合とローカル再現

`eventLedger.ts`の実際のparseLedger・inspectLedgerへ固定原文と関係行を入力し、以下を確認した。外部LLMは呼んでいない。

| 関係種別 | 主体 | リソース／実施状態／受領確認 | 現行結果 |
| --- | --- | --- | --- |
| before | 両端`-` | `- / - / -` | 「実施状態・受領確認が不正です。」 |
| before | 両端`-` | `- / occurred / na` | 正常 |
| dependency | 正しい両端主体 | `- / - / na` | 正常 |
| dependency | 正しい両端主体 | `- / occurred / na` | 「実施状態・受領確認が不正です。」 |
| dependency | 両端`-` | `- / - / na` | 「伝達・影響には両端の主体が必要です。」 |

繰り返し同じ種類の警告が出る原因として、単なるモデルの不安定さだけでなく、次のアプリ設計上の問題がある。

### 2.1 種別ごとの属性規則が分かりにくい

プロンプトは空欄を一律`-`と説明し、実施状態を一般にoccurred/omitted/unknownと説明している。一方、dependencyの実施状態は例外的に`-`、受領確認はnaでなければ拒否する。

beforeについては主体の省略だけを説明し、意味上は不要なリソース移動・実施／受領属性をどの値にすべきか明確でない。検証側はbeforeにも実施状態の列挙値を要求する。そのため、意味上は自然な「時間順なので対象外」を形式エラーとしてLLMへ再取得する。

### 2.2 主体・客体の区別と関係端点の規則が離れている

機器が客体のみならレーンを作らない、主体不明ならイベントを保持する、という指示はある。しかし、関係表ではbefore以外の全種別に両端主体が必要である。LLMがイベント間の関係だけを示し主体を`-`にすると、R9の警告になる。主体不明をアプリが推測して埋めてはならない。

### 2.3 警告に原因を特定する情報が足りない

現在の複合条件は、dependencyのリソース不正でも「実施状態・受領確認が不正」と出す。両端主体の不足はmutual/common/dependencyでも「伝達・影響」と表示する。行IDだけでは、どの種別・列・値が原因か分からず、利用者にも修復LLMにも説明が不十分になる。

### 2.4 契約が複数箇所に散在している

通常抽出、接続提案、連鎖差分修復、保存読込で別々に属性条件を実装している。プロンプトも組込・public/prompts.json・既存のカスタム設定・実行時の追記で組み立てるため、現行ルールと実際に送ったルールが一致しているか追いにくい。

### 2.5 修復は通信待ち時間を増幅する

初回応答は約23秒。意味の変更を必要としない対象外属性の表記でも再照会しており、入力より短い応答でも再試行が頻発し得る。警告の非表示や回数の増加では、原因と待ち時間は解決しない。

### 2.6 追加ログで確認したエラー対象の誤拡大

追加ログでは、最初はR2～R6・R9、修復後はR1～R8が依存関係エラーとなり、次の修復で再び実施状態エラーへ変わっている。再実行でも、属性エラーを直した後にR1～R6へ依存関係エラーが拡大している。

コードでは、TSVの局所検証でissuesがあれば、その時点で返す。局所検証を通った後でvalidateParticipantsによる関係の意味・参照検証を行い、そこで例外が出ると、inspectLedgerのcatchが関係表の全行へ同じmessageを付ける。このため、局所検証を修復した後に隠れていた意味検証エラーが現れ、正常行まで不正行として修復対象に混ざる。

実際の関数を使って以下を再現した。

1. R1は正常なbefore。R2は両端が同じ主体のdependencyで、現行の意味検証では不正。R3は実施／受領が対象外表記のbefore。
2. 初回検証はR3の「実施状態・受領確認が不正」だけを返す。R2の意味エラーはまだ検査されない。
3. 指定どおりR3だけを修復する。R1には一切変更しない。
4. 次の検証でR1・R2・R3全てに「作業依存の端点または属性が不正」を返す。

この再現は、追加ログの個別行の値を確定するものではない。しかし、正常行へ警告を誤配布し修復対象を拡大させるアプリの不具合は確認できた。「LLMが正常なR1まで書き換えた」とは、このログだけから判断できない。

1回目は初回通信約23.1秒＋修復約80.1秒で失敗。再実行は初回約41.4秒＋修復約25.8秒で失敗している。2実行の通信待ち約170.4秒のうち約105.9秒が修復であり、修復回数を増やすより、誤った対象拡大と契約の不一致を直すべきである。

## 3. 改善する関係契約

単一の`relationContract.ts`を追加し、種別ごとの必須端点・適用属性・許容値・説明を定義する。プロンプトと各検証器が同じ定義を参照する。

| 種別 | 主体端点 | 新規出力のリソース | 新規出力の実施状態 | 新規出力の受領確認 |
| --- | --- | --- | --- | --- |
| before | 省略可。イベント両端は必須 | `-` | `-` | `na` |
| dependency | 両端必須、別イベント・別主体 | `-` | `-` | `na` |
| transfer | 両端必須 | information/material/person/money/other | occurred/omitted/unknown | confirmed/unconfirmed/na。原文に対応した値 |
| impact | 両端必須 | 現行の適用可能な区分。対象外は`-` | occurred/omitted/unknown | 受領という概念がなければna |
| mutual | 両端必須 | 現行区分。対象外は`-` | occurred/omitted/unknown | 対象外はna。相互確認の実施を推測しない |
| common | 同一イベントの両端主体が必須 | 原則`-` | occurred/omitted/unknown | na |

beforeの実施状態`-`を正規に受け付け、内部では未設定とする。対象外の受領確認について、beforeの`-`はnaと同義な輸送上の表記として受け付ける案とする。これは発生・受信の事実を補う処理ではない。dependencyのnaも、共通契約に「対象外」を表すトークンとして明記し、空欄一般の説明より優先する。

既存のbefore行でoccurred/omitted/unknownが入っているデータは既存契約として読めるようにする。保存済み図を勝手に移行・上書きしない。beforeの状態値は、リソース送受信の証拠に使わない。

各意味属性の適用範囲の厳密化は、新規出力の契約版を付けて実施する。既存の正常データを新規出力用の制約で突然拒否しない。保存読込の互換検証と、新規LLM出力の検証は呼出しモードを分ける。

実際の送受信や実施状態が不明なtransfer等に対し、`-`をoccurredへ置換する、端点を近いレーンで埋める、任意の略語・日本語を意味推測で列挙値へ変える処理は行わない。

## 4. プロンプトと修復指示

### 4.0 行別エラーの確定を最優先にする

共通検証器は例外の文字列だけでなく、関係ID・列・理由コードを持つ結果を返す。1行の意味エラーを、例外が出たという理由で全関係行へ展開する処理を廃止する。関係行が不正ならその行だけを対象にし、循環や共有カードの矛盾など複数行にまたがる問題は実際に関与するID集合を返す。

局所の列・属性検証と、参照・端点・意味検証の条件を共通契約へ集約し、同一の行が一段目と二段目で異なる属性条件を要求されないようにする。形式と参照が有効な行については、1回の検証で判明する問題をまとめて返す。不正参照で後続の意味検証ができない行は保留し、そこから正常行へ連鎖的なエラーを作らない。

正常行は、関係表全体の検証が完了する前にも、再取得対象へ入れず保持する。正常行の削除・review化・再生成を、例外からの回復手段として使わない。修復後は全体整合を再評価するが、新しい問題を正常行へ一律に付け直さない。

### 4.1 初回の指示

長い一般説明に例外を積み重ねる方式を改め、以下の順に整理する。

1. 意味上のルール：事象分離、主体／客体、帰結保持。
2. TSV表の列定義。
3. 上記の関係種別別属性表。
4. before、dependency、transferの短い正常例。例のID・内容をコピーしない指示。
5. 主体不明の関係は出力せず、イベントを残して整理reviewへ返す例。

「実施状態は3値」と書く箇所を「transfer等に適用」と限定し、before/dependencyの`-`と矛盾させない。主体が必要な種別へdependencyを明記する。受領確認のconfirmedは、原文で受信・確認が記録されている場合に限定する。

### 4.2 修復の指示

構造化したエラーを使い、例えば次の内容を渡す。

- `R2 / before / 実施状態 / 受信値=- / 新契約で対象外として有効`：LLM修復不要。
- `R3 / dependency / 実施状態 / 受信値=occurred / 許容値=-`：その列を含む行だけ修復。
- `R9 / dependency / 元主体=- / 両端主体が必要`：原文から特定できれば修復。特定できなければ同じIDの整理reviewへ移す。

関係行をreviewへ移す場合も、正常イベント・帰結は削除しない。既存の対象行のみ置換・指定外変更禁止・最大2修復・無進展停止を維持する。

## 5. 原因を追えるログ

`LedgerIssue`に、エラーコード、関係種別、列名、実際の値、許容値を追加する。機微情報の入りやすい本文全体ではなく、問題の列の値だけを長さ制限付きで表示する。原文・応答全文・APIキーは通常ログへ出さない。

ログは「対象外表記の受入」「LLMによる行修復」「根拠不足で要確認」「最終失敗」を区別する。対象外として有効な表記を受け付けた場合は、繰り返し警告するのでなく集約したinfoにする。本当に必要な列や根拠の不足を警告から隠す変更はしない。

実行ID、方式、契約版、実効プロンプトの指紋、モデル、関係種別別のエラー件数、修復回数・追加待ち時間を記録する。既存カスタム設定の使用有無も分かるようにし、古い契約へ新指示を黙って重ねるのではなく、版の整合を開始前に確認する。カスタムプロンプトは上書きせず、必要な更新箇所を利用者へ示す。

## 7. 受入条件と効果測定

1. beforeに`- / - / na`、対象外の`- / - / -`が返っても、意味を追加せず再照会なしで受け入れる。
2. 既存のbeforeの状態値を持つ5.0データを読み込める。
3. dependencyのoccurredや不足主体は、種別と問題列を示して限定修復する。主体はアプリが推定しない。
4. transfer等で受信の事実が不明なとき、confirmedへ自動変更しない。
5. 修復できない関係はreviewへ移し、イベント・帰結・正常関係を保持する。
6. 1件の不正関係で、全イベントの再抽出や全関係の再生成を要求しない。
7. 通常抽出・接続提案・差分修復で、同じ種別・属性の組合せの判定が一致する。保存互換モードの差は明記する。
8. 組込・public・dist・ZIP内の契約とプロンプトが一致し、古いカスタム設定の利用を識別できる。
9. 元のR2～R6・R9のTSVが得られたら実値を再現データへ追加し、推定原因と一致するか確定する。
10. 第2.6節の3行の再現で、正常なR1を修復対象にせず、R2だけの意味エラーを識別する。R3が局所検証で不正な間も、検査可能なR2の問題を見落とさない。
11. 関係の循環等はその循環へ参加する行IDを返し、無関係なbefore・transferへ同じエラーを配布しない。
12. 修復後に値が以前の不正状態へ戻る往復を記録し、同じ行の同じ不正状態を再修復し続けない。実効契約版を含む履歴から無進展と矛盾を示す。

実モデル評価では、初回の有効行率、警告の種別別件数、修復呼出し数、修復による追加待ち時間、修復後の成功率を記録する。形式だけ通ってイベント・主体・関係・帰結の意味が悪化していないかも原文照合する。同一資料・同一モデル・同一設定の複数実行で比較し、単にログのwarnをinfoへ変えただけの改善を成功としない。

## 8. 自己点検

- 通信成功と、アプリが台帳を受け入れられることを分けて説明した。
- ログから個別行の値は断定せず、実際の検証器で同一警告の発生条件を再現した。
- 機械処理は対象外値の輸送上の解釈と参照検証に限定し、意味の修復はLLMに任せる。
- 状態値を厳格にする部分と、既存データの互換読込を区別した。
- 修復回数を増やす対策ではなく、曖昧な契約と不要な再通信の削減を優先した。

## 8. 実装結果（2026-10-29）

- 関係の列・属性・主体端点と意味検証を行別に実施する。局所エラーが残っていても検証可能な別の関係行を検査し、正常行へ例外を一括配布しない。before循環は循環中の辺、共有カード重複は実際に重なるグループを対象にする。dependency相互間の循環も検査する。
- relationContract.tsで種別・属性・端点の規則を共通化し、台帳、接続提案、差分修復、保存検証から利用する。beforeの対象外状態・受領表記を受け入れる。保存済みの任意属性の省略や既存before状態値は保持し、旧形式変換は追加しない。
- 組込・外部正規化プロンプトと修復入力に関係属性契約版・種別表・例を含める。差分修復と接続提案には各出力形式に合わせて契約を補足する。保存済みカスタム設定へ契約が未反映ならinfoで通知し、実行時の指示で現行契約を優先する。カスタム設定原本は書き換えない。
- 警告と修復指示に関係種別・問題列・長さ制限付き受信値・許容値を含める。実行ID・モデル・契約版・実効プロンプト指紋、成功時の修復回数・追加待ち時間を記録する。正常なイベント・関係・帰結を保持し、最大2修復と変更なし／以前の状態に戻る修復の停止を維持する。
- ローカル再現と疑似LLMによる試験を追加。全64ファイル419テストと型検査が成功。実際の利用者の受信TSVは未取得であり、実モデルでの警告発生率や待ち時間の削減率は未測定。
