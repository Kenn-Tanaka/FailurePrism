## 1. 到達点と今回の範囲

新規生成に`event-chain`方式を追加する。原文全文から、分析対象・個別事象・主体・割当・関係を一体で生成し、根拠付きの連鎖を確認画面へ返す。根拠不足で連結できない場合も下書きを保持し、未完成と明示する。

共通処理には、方式に依存しない構造診断、意味上の関係の投影、連結性を保つ表示整理、確認・保存・出力を置く。既存`fulltext-ledger`方式も選択可能にし、同じ診断を適用する。レーン間の隣接限定は両方式と既存図のAI提案から撤回する。同一レーン内の隣接ノード接続・飛び越し禁止は維持する。

実装する不足点検は、関係追加に加え、抜けたイベント・主体・割当を差分提案できる範囲とする。既存の正常イベントの自動削除・融合・ID変更は扱わない。分割が必要な既存イベントは確認事項として提示し、既存の手動編集で直した後に再点検する。

## 2. データ契約を先に確定する

帰結の欠落対策として、`analysis.outcome`（identified/not_found/uncertain、イベントID、原文参照、理由）と正規化TSVの任意`[帰結]`セクションを先行追加した。新規指示では帰結確認行を要求し、既存データにない場合は未確認として表示する。帰結候補を分析対象へ自動確定する処理ではない。確認画面で、未抽出・未確認と、抽出したが未割当で図に出ない状態を区別する。イベント・主体を含む差分修復の未実装事項は引き続き残る。

### 主体と客体の採用規則（利用者指摘による補足）

機器がイベントへ関与するだけでは、レーンに採用する主体とはしない。操作・試験・製造・運搬の対象、被制御対象、被害物は客体としてイベント本文と原文参照へ残す。搭載機器の破損という文法上の主語だけで機器レーンを作らない。原文で試験・操作主体との対応が分かる場合は、その部門等へイベントを割り当てる。対応不明ならイベントを未割当・要確認として保持し、責任主体を推定しない。

自動検知・制御判断・信号送受信・自律動作・他への作用等の担い手として原文に記録された機器は、必要ならmachine主体とする。同じ機器が別イベントでは客体になる場合もある。将来の台帳・差分提案でもこの区別を適用し、全体連結のために客体を主体へ昇格させない。既存図の機器レーンは自動削除・自動移動せず、根拠付きの割当修正を確認して採用する。

現在の修正はLLMへの意味判断指示であり、機器名やmachine属性を条件に機械的に除去する処理ではない。固定応答テストは指示の送信と結果保持を検証し、実LLMでこの事例を適切に抽出できるかは別途評価する。

### 2.1 保存形式と互換性

Project `5.0` / analysis `5`を維持し、下記の任意属性だけを追加する。既存のイベント・主体・関係・カードの意味と必須属性は変えない。旧5.0では追加項目を未設定として読めるようにし、必要な分析対象の選択を促す。5.0より前の読込・変換は追加しない。

`validateSavedAnalysis`、プロジェクト読込、下書き復元は任意項目を検証・保持する。参照不正などの破損と、分析対象未設定・未連結・要確認ありを分け、後者を理由にファイル全体の読込を拒否しない。

旧リリースへの逆互換は保証しない。任意属性がないことを根拠に、現行方式で生成した、確認済みである、と推測しない。

### 2.2 追加する型

| 保存先・新設型 | 主な属性 | 規則 |
| --- | --- | --- |
| `analysis.context?: VTAAnalysisContext` | `objective`、`targetCandidates[]`、`selectedTargetEventIds[]`、`scopeDecisions[]` | 分析目的は入力文。対象候補はイベントID・原文参照・理由。選択対象は既存イベントを参照 |
| `scopeDecisions[]` | 対象種別event/entity、対象ID、`include/exclude/review`、理由、`llm/user`の由来 | LLMの除外提案は候補として保持。分析範囲を実際に縮めるのは利用者が採用した決定だけ |
| `VTAEventRelation.explanation?` | 短い説明 | 原文のどの行為・状態が、相手の何に関係するか。LLM理由を利用者の確認理由と区別 |
| `VTAEventRelation.evidenceBasis?` | `recorded/source-assessment/user` | 記録された関係、入力資料にある評価、利用者の追加判断を区別。LLMの自信度を事実属性にしない |
| `analysis.reviewItems?` | ID、コード、イベント／主体／関係ID、原文参照、理由、解決記録 | 原文上の矛盾・不足・主体／関係未確定。解決には根拠または明示的な範囲決定が必要 |
| `analysis.review?` | 確認した内容の署名、利用者の確認理由 | 内容が変われば確認は失効。単なるbooleanの「確認済み」は保存しない |
| `generation` / `generationRuns` | 方式ID・版、ルール版、台帳契約版を識別する情報 | 既存来歴を維持し、部分修正で図全体を新方式生成と記録しない |

`selectedTargetEventIds`は同一事故・不具合の複数の表現を選べるが、無関係な独立事故を接続する手段にはしない。独立事故が混在する場合はreviewItemsで分析の分割を促す。未選択時は構造診断のみ実行し、対象確認待ちとする。

対象イベントは範囲に含め、既存の割当カードを一つ以上必要とする。共有イベントのレーン別カードを選んで別事故として扱わない。イベントの範囲除外は対応カード全てに作用し、主体の範囲除外はその主体の関与だけに作用する。分析対象が無割当になる、または対象事象の関与を失う除外は採用せず確認事項へ戻す。

新規生成は全抽出イベント・主体を暫定的に対象とする。LLMが範囲外と提案しただけで、事故に必要な主体を消さない。範囲除外は`presentation.lanes=hide`と別の操作とし、原データは残す。

### 2.3 完成判定の状態を分離する

表示は次の独立した評価から導出し、保存した完成フラグを信用しない。

- 構造：`target-unset / disconnected / connected / invalid`。
- 表示：`complete / user-filtered / auto-simplification-gap / projection-gap`。
- 要確認：未解決事項の件数・対象。
- 利用者確認：`pending / current / stale`。

「利用者確認済み」でも構造不足は残り得る。完成と表示する条件は、対象確定、構造連結、投影不足なし、未解決の分析上の問題なし、現在の内容への利用者確認、である。利用者の意図した非表示は表示限定として別表示する。ゼロイベント・ゼロレーンは連結した図として合格させない。

## 3. 台帳と方式の契約

### 3.1 `chain-ledger-1`の入力・出力

既存方式の5セクション契約と新方式の契約を明示的に区別する。新設`chainLedger.ts`で`chain-ledger-1`を解析し、TSVの字句処理・ID・参照検査は現行処理から共通化する。形式不明時に他の契約へ自動フォールバックしない。

既存の主体3列、イベント7列、関係10列、共有カード3列、整理5列を再利用し、以下を加える。新方式の全原文参照は`sourceId/paragraphId`とする。旧方式の`p1`参照は旧アダプター内に留める。

| セクション | 列（タブ区切り） | 用途 |
| --- | --- | --- |
| `[分析対象]` | ID・イベントID一覧・原文参照・理由 | 対象の候補。候補IDとイベントIDを混同しない |
| `[範囲確認]` | ID・対象種別・対象ID・提案include/exclude/review・原文参照・理由 | 対象範囲の提案。excludeは採用まで効力を持たない |
| `[関係説明]` | ID・関係ID・根拠区分recorded/source-assessment・原文参照・説明 | 関係と1対1で対応。user由来はLLMが出力しない |
| `[要確認]` | ID・対象ID一覧・原文参照・コード・理由 | 不足・矛盾・対象不明など。新規の事実としてイベント表へ入れない |
| `[完了]` | 行終端の単独記号 | 途中応答を検出する |

新方式の関係は安定したIDと関係説明を必須にし、source/targetのイベント・主体割当があることを確認する。dependencyではresource/statusを`-`、receiptを`na`とする既存の区別を維持する。旧データに説明欄がなくても読めるが、説明があるように補完しない。

意味の判断はLLMが行う。アプリは参照先と属性・構造を確認する。送信済み段落の存在は、関係が正しいことの証明とは表示しない。

### 3.2 一回の生成と再点検

1. 原文全文、分析目的、既指定の対象、モデル、プロンプト、方式と契約の版を固定する。
2. LLMが全文から1パスで台帳を構成する。通常作業・未実施・複数主体の役割・非隣接関係を点検させる。
3. 形式・ID・参照の不備は指定行だけ最大2回修復する。関係が特定できなければ要確認へ移し、正常イベントを捨てない。
4. 共通検証・全関係の投影・構造診断を実行する。対象未選択なら、LLMの対象候補ごとの連鎖を暫定診断し、初期抽出時に分析対象を勝手に確定しない。
5. 対象確定後、必要な場合のみ「連鎖不足をAIで点検」を実行する。既存図の点検も同じ入口を使う。

初回の全文生成に加え、**一回の連鎖不足点検操作では意味上の再点検を最大2パス、操作全体のLLM呼出しを最大6回**とする。形式修復も6回の枠へ含め、上限到達時は正常な下書きと未解決事項を返す。通信失敗を自動再送して回数上限を迂回しない。通信回数・用途・所要時間をログへ出す。

初回の形式修復は最大2回、従って初回生成は最大3呼出し。初回処理から不足点検を無断で連鎖起動しない。利用者が対象を確認した後の点検操作として分け、長時間の処理を見通せるようにする。

再点検には、原文全文の固定スナップショット、全ての現在のID、分析対象、成分・不明事項、採用済み関係、削除・非表示・範囲の利用者決定を渡す。入力上限を超えた場合は開始前に対象を絞る案を示し、原文を黙って切り捨てない。途中で上限へ達した場合も下書きを保持する。

## 4. グラフ診断の具体化

新設`graphDiagnostics.ts`は副作用のない関数とし、診断のためにLLMを呼ばず、ノード・線・表示設定を書き換えない。

### 4.1 入力モデル

`buildGraphSnapshot(schema, scope)`が次の3層を構成する。

| 層 | 頂点・線 | 主な目的 |
| --- | --- | --- |
| 正規の有効グラフ | 範囲内の全カード・接続点。採用済み意味関係、共有イベントの同一性、生成規則上必要な同一レーン隣接線。明示削除を反映 | 分析として接続が不足していないか |
| 期待する投影 | 正規関係・有効な共有関係・同一レーン隣接規則から算出する線のID／端点 | 正規関係が実際の図へ投影されていない不具合の検出 |
| 現在の表示グラフ | 実際の表示ノード・接続点と実際に表示する線 | 非表示・整理・投影失敗で切れていないか |

関係の参照不正や端点が一意に決まらない場合は無効線として列挙し、接続数へ含めない。別イベント間の意味未判定線は、見かけの連結を作っていても分析の完成根拠へ含めない。手動関係は明示した意味・端点を利用者の判断として扱い、原文参照なしならその由来を明示する。

`before`は順序制約だけとし、レーン間接続線へ変換しない。共通イベントの無向線はイベント同一性の根拠だけで連結に数えるが、因果・移動・BREAK効果の根拠にはしない。未実施の予定関係は未実施と分かる線として扱い、起きた移動と同一視しない。BREAKは分析図上の対策属性なので線の存在を消さない。排除指定したノードも、反実仮想の計算と別に実際の経過として数える。

削除済み関係を「正規関係に残っていた」という理由で有効グラフへ復活させない。削除前なら連結することは、削除が影響したという診断材料にだけ使う。レーン非表示は正規グラフを変えず表示グラフだけへ反映する。

### 4.2 結果型とアルゴリズム

`GraphDiagnostics`には以下を返す。

- 正規／表示それぞれの`components[]`（カード・イベント・主体ID、対象事象を含むか）。
- `isolatedEntityIds`、`unassignedEventIds`、空の明示表示レーン。
- `missingProjectionRelationIds`、`ambiguousEndpointRelationIds`、同一レーンの不足／飛び越し。
- `targetIssues`、`temporalContradictions`、未解決の`reviewItems`。
- 表示分断に関係する非表示主体、整理カード、削除線。複数要因なら全て記録。

連結成分は隣接リスト＋BFS/Union-FindでO(V+E)を目標にする。レーン単位の成分は補助表示であり、ノード単位の検査を省略しない。未割当イベントはグラフに載らなくても問題として残し、カード化されていないために合格する抜け道を防ぐ。

構造上の「連結」と、意味上の「対象事象との関連」を別診断にする。全イベントから最終事象への有向経路を機械的に強制しない。リソースの受渡し方向・共通影響・事故後の作業を考慮すると、全イベントの有向到達は正しい一般条件にならない。

同一イベント・同一カードグループを正しく扱った時間制約グラフで循環を調べる。台帳順のフォールバックだけと逆向きであることをもって矛盾とせず、原文に基づくbefore等との衝突を区別する。依存線を採用するために元のイベントを統合して循環を消さない。

## 5. 投影と表示整理の変更

新設`buildGraphProjection`を`projectAnalysis`から呼ぶ。処理順序を固定する。

1. 全イベント・主体・割当から正規カードを作る。
2. 安定した関係IDから全ての意味関係の投影を構成する。手動属性・削除指定・BREAKを反映する。
3. 全カードを対象に共有イベントのまとまりと、同一レーン隣接線を計画する。
4. 自動整理の各候補について、整理前後の対象主体・連結成分・イベント代表の保持を検査する。
5. 整理結果を適用し、表示ノード間の共有線・隣接線を再構成する。
6. 正規・期待投影・表示の診断結果を返す。

`edges.some(source,target)`による一括抑制をやめ、意味関係は関係IDで投影・編集・削除する。無向関係の重複キーは端点ペアを保持して正規化し、方向付き関係は向きを保持する。異なる関係を一本に見せる場合も、内部の複数関係IDは失わせない。初期実装は線を別々に保持し、経路・ラベルをずらす。

同一レーンの時系列線と同じ端点に意味関係がある場合は、その関係の描画だけで隣接の構造要件を満たせる。時系列だけを意味関係へ昇格させる逆方向の処理はしない。別の意味関係が複数あれば全て保持する。

今回、自動整理で分析範囲内の非空主体を空レーンへして隠すことは禁止する。単独カードが他レーンの同じイベントと重複していても、その主体の関与が必要なら残す。利用者の範囲除外または明示非表示は別に尊重する。表示グラフの連結維持を理由に、隠した主体を経由した移動を別主体間の直接矢印へつなぎ替えない。

通常の編集・投影では新たな自動整理をせず、初回生成と利用者が指定した整理操作だけで実行する。診断計算からprojectAnalysisを再帰的に呼ばず、純粋な投影スナップショットを共用して無限更新を防ぐ。

## 6. 不足点検の差分契約

現行の関係だけを追加する13列TSVは残し、レーン間の隣接必須検証を外す。新設`chainRepair.ts`はイベント・主体・割当も扱える専用差分とし、以下を返す。

| セクション | 許可する変更 |
| --- | --- |
| `[追加主体]` | 5列：ID・名称・種類・原文参照・理由 |
| `[追加イベント]` | 7列：ID・時刻・見出し・内容・原文参照・区分・理由。割当は別表で指定 |
| `[割当追加]` | 6列：ID・イベントID・主体ID・役割・原文参照・理由 |
| `[関係追加]` | 12列：ID・種類・元イベント・元主体・先イベント・先主体・原文参照・リソース・実施状態・受領確認・根拠区分・理由 |
| `[要確認]` | 5列：ID・対象ID一覧・原文参照・コード・理由。分割必要、主体同一性不明、関係不明、対象範囲の相談を含む |

この差分契約は`chain-delta-1`とし、全セクション（空でも見出しを残す）と末尾`[完了]`を必須にする。既存の関係だけの13列提案と同じパーサーへ無条件に渡さない。関係追加のbeforeは順序だけを表し、主体が不要なら`-`とする。他の種別は両端の主体割当を必須とする。`[追加主体]`・`[追加イベント]`・新規関係のIDは一時ID、割当行・要確認行のIDは差分内の行識別子として扱う。

一時IDは`tmp_`接頭辞に限定し、採用時にアプリがUUID等の永続IDへ写像する。既存IDの再定義・別イベントへの使い回しを拒否する。新規主体は同名という理由だけで既存主体へ統合せず、候補照合を利用者に示す。新規イベントのsourceOrderを末尾へ単純追加せず、LLMが示した既存イベントとのbefore・原文位置を含む順序提案を表示し、採用後に全体順序を再評価する。

既存図の全データ、手動関係、削除・非表示・範囲決定を固定し、候補を一時コピーへ適用してから共通検証・診断する。上流の新規イベント／主体を選択解除した場合、それを参照する関係だけの採用を許可しない。適用単位を依存する候補群として提示する。

削除した依存の同一意味キーを別IDで再追加しても採用を拒否する。旧形式の線IDだけの削除履歴も、保存中に対応関係を特定できる場合は照合し、分からない履歴を推測して復元しない。

2パス目は1パス目の有効差分を一時コピーにだけ取り込んで点検する。利用者の図へは途中適用しない。ID順や理由の言い換えだけを進展とせず、参照・割当・関係・未解決事項が実質的に変わらなければ停止する。根拠なしの線追加や主体除外で成分数が減っても有効な改善と扱わない。

利用者の選択後、全選択を合わせた循環・端点・重複・削除履歴・診断を再確認する。一部だけ採用して連結しなければ「不足あり」のまま適用できる。適用は1トランザクション・1Undoとし、確認済みと完成を自動で同一視しない。

## 7. 共通実行・画面・保存

### 7.1 生成方式の実体化

`services/generation/schemes.ts`に方式定義を一箇所で登録する。現在`client.ts`の全文抽出と部分再抽出でそれぞれ生成しているローカル登録を共通ファクトリーへ移す。`GenerationScheme`に`generate`、対応時のみ`restorePassage`、診断後の不足点検への接続を明示する。`supportsPassage`という表示値だけでなく実際のハンドラーを照合する。

event-chainは`chain-ledger-1`、fulltext-ledgerは既存契約を使う。プロンプトは契約版を明示して登録し、未知の版や空のカスタムプロンプトは開始前に説明して止める。旧カスタムの黙った上書きはしない。組込と`public/prompts.json`の一致をテストする。

既存方式を選んでも、共通の構造診断・保存・出力を省略しない。event-chainで生成した既存図への部分再抽出も方式のハンドラーから実行し、全体のID・順序・診断へ統合する。別方式へ黙って切り替えない。

### 7.2 画面と状態

- `ScenarioInputSection`：生成方式と分析目的を入力。新規生成はevent-chainを既定とする。実装済み2方式だけを表示し、方式変更だけで既存図を置換しない。
- `EventReviewPanel`：分析対象候補、対象範囲、イベント／主体、構造診断を表示。対象候補を変更したら再診断する。通常／変動の判定は従来どおり別操作。
- 新設`GraphDiagnosticsPanel`：成分ごとに対象・レーン・カードを表示。原文へ辿り、「連鎖不足をAIで点検」を実行できる。
- 新設`ChainRepairModal`：追加前後の成分、根拠、差分、依存する候補群、残る問題を示す。初期未選択。既存の関係だけの提案画面と明確に区別する。
- `LaneManagementPanel`：表示非表示と分析範囲を別操作として示す。非表示による分断は通知し、自動解除しない。
- キャンバス：構造不足／表示限定／確認状態を短く表示。保存と通常編集は継続可能。「完成として確認」と「不足を残して反映」を区別する。

意味上の内容の署名には、原文、分析対象・範囲、イベント本文・時刻・順序・主体割当・カード構成、関係・根拠、手動線・削除指定を含める。座標・ズーム・列順・LLM進捗・生成日時は除く。確認済み属性自身も署名から除き、自己参照を避ける。表示状態は別の署名で診断を更新する。

処理開始時の実行ID・プロジェクト・内容署名・モデル・方式・実効プロンプトを固定する。応答時と採用時に再照合する。入力・対象・関係が変わった古い結果は失効。位置移動だけで根拠付き提案を失効させない。修復キャッシュは操作種別・方式版・契約版・対象・原文・実効プロンプト・モデルで分ける。

### 7.3 出力と履歴

`computeVTADataHash`へ分析対象・範囲・意味上の説明・確認事項を追加する。図の表示変更だけでは意味上のレポートを古くしないが、表示診断とSVGは再計算する。診断結果そのものをハッシュへ再帰的に入れない。

SVGは見出し出力を無効にしても、未完成・表示限定の注記を別要素で表示し、metadataにも対象と不足件数を記録する。見出し非表示が不足表示を隠す抜け道にならないようにする。

`reportContextExtractor`の配列だけでなく、実際の文章化関数へ種類・理由・原文参照・不足状態を渡す。現在の文章化には無向線を一方向矢印にする分岐があるため修正する。共通イベントのまとまりや未実施を「実際の伝達があった客観的事実」と一括説明しない。中立線だけからBREAKの有効性を生成しない。

下書き保存、ファイル保存読込、Undo/Redo、取り消し、SVG、レポートで新属性を維持する。既存の手動位置・接続点・補足・対策を保持する。診断の再計算だけでは履歴やisDirtyを増やさない。

## 9. 検証の具体的な組合せ

| ケース | 期待結果 |
| --- | --- |
| A-BとC-D、各レーンに他レーン線あり | ノード・レーンとも複数成分。完成にならない |
| 同じレーンの途中が切れた図 | レーン集約で見えない分断も検出 |
| 非隣接の手順書作成→使用 | 原文参照付きの依存を許可。中間の同一レーンノードは保持 |
| 近い時刻の無関係な作業 | 関係を創作せず不足・要確認を保持 |
| 通知未実施・仕様未反映・受信未確認 | 実際に受渡しが起きたと表示・文章化しない |
| 未割当のイベント、対象未選択、ゼロイベント、空レーン | それぞれ別の診断。空集合を完成としない |
| 共有イベント・双方向確認・接続点・BREAK・排除指定 | 同一発生を時間循環へ変換せず、対策指定で実経過を消さない |
| 同じ端点のtransferとdependency | 両方の関係ID・理由・表示を保持 |
| 単独共有カードが主体の唯一の接点 | 自動整理で主体ごと消さない |
| 手動非表示・線削除で分断 | 意図を尊重し、復元しない。原因と不足を表示 |
| 削除済み依存を別IDで再提案 | 意味キーで検知し、無断採用を拒否 |
| 新規イベント候補を外し、その関係だけ選択 | 原子的採用を拒否。必要な候補を案内 |
| 同じIDで別イベントを返す／既存イベントを融合する | 応答を拒否して正常な下書きを保持 |
| 改善しない修復・形式エラーの繰返し・504 | 上限・無進展停止。既存図と正常候補を保持 |
| 入力・対象・プロジェクト変更、再実行、位置移動 | 内容変更／旧実行は失効。位置だけの変更は失効させない |
| 利用者が確認した未連結図 | 確認済みでも未完成と表示 |
| 事故後の救助・調査、複数の独立事故 | 最後の時刻を対象と誤認せず、分割要確認を提示 |
| SVG見出しなし、無向線を含むレポート | 不足注記を保持し、無向線を矢印や伝達済みに変えない |
| 保存・下書き・再読込・Undo/Redo・未知の方式来歴 | 新属性・手動配置を保持。未搭載方式でもデータは閲覧可能 |

試験データは`tests/vta/fixtures/event-chain/`へ原文・固定TSV・期待する成分と診断コードをセットで保存する。リポジトリの小サンプルを構造回帰に使い、今回の利用者の孤立事例と同一と称さない。実際の入力と保存結果が得られた時点で再現データを追加する。それまでも非隣接依存・複数成分・未連絡の合成例で実装を進められる。

JAXA抜粋は設計根拠の参照資料であり、事故の入力原文として学習・抽出の期待結果へ混入させない。固定応答の合格はLLMの意味判断品質の証明と区別する。実LLM評価では必要関係の欠落・誤接続・事象融合・必要レーン脱落・未実施誤認を原文照合で記録し、単なる連結率を品質基準にしない。

実装完了時は`npm run typecheck`、`npm test`、テスト省略なしの`build.bat`を実行し、distとZIPの契約版・プロンプト・診断表示が一致することを確認する。依存パッケージの追加は予定しない。

## 10. 実装計画の自己レビュー

結論：事象連鎖中心の方針は妥当だが、修正案のままでは状態・範囲・削除・差分採用の境界が不十分だった。以下を本書へ反映してから実装する。

| 重要度 | 発見した問題 | 本書へ反映した修正 |
| --- | --- | --- |
| 高 | 「確認待ち／不足あり／確認済み」を排他的状態にすると、確認操作で未連結が完成へ変わり得る | 構造・表示・要確認・利用者確認の4軸で評価する（2.3） |
| 高 | 最終事象候補や範囲外提案をそのまま採用すると、LLMが必要レーンを除いて連結率を上げられる | 対象候補を確認待ちにし、分析範囲を縮めるのは利用者の採用のみ（2.2、3.2） |
| 高 | 正規関係があるだけで連結とすると、明示削除・未投影・曖昧端点を見落とす | 有効グラフ・期待投影・実表示を別計算し、削除を尊重（4） |
| 高 | 初回抽出が対象未選択のまま再点検を続けると、誤った最終事象へ修復を収束させる | 初回は対象候補の生成まで。確認後の操作として不足点検を行う（3.2） |

| 高 | 再点検2回に各形式修復を無制限に重ねると長時間化する | 操作全体6呼出し上限と意味上の再点検2パス、初回3呼出しを明記（3.2） |
| 中 | 現行の登録表はclient.ts内で都度組み立てており、対応操作の実体も共通化されていない | 静的定義＋共通ファクトリー、実ハンドラーによる対応判定へ変更（7.1） |

| 中 | SVG見出し非表示やレポート文章化で意味・不足が消える | 独立注記、無向／未実施の文章化、BREAK候補の扱いまで変更対象（7.3） |

未検証の外部条件：利用者が観測した孤立事例の実際の入力・保存結果、および実LLMの生成品質。これらが未入手でも構造診断と固定応答試験は進めるが、当該事例が解決したとは報告しない。
