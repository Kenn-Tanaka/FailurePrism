# VTA テキスト変換・TSV台帳 実装仕様と自己点検

2026-10-29。イベント抽出の現行仕様。従来のJSON正規化応答と引用完全一致検証を使う抽出経路を置き換える。

## 1. 処理と責務

1. アプリが入力原文を保持し、段落を `[p1] 原文` の形式でLLMへ渡す。日付や見出しの書式を前提にしない。長い行の分割は参照位置を付けるためであり、LLMには全文を一回で送る。
2. LLMが正規化、独立イベントの分離、主体同定・役割、時刻と順序、伝達・影響、背景・除外・要確認を決め、TSV台帳へ変換する。
3. アプリが列数、列挙値、IDの一意性・参照先、描画不能な前後関係の循環や矛盾を確認する。引用文の完全一致、日付の解釈、段落先頭からの時刻補完、段落ごとの強制的なイベント生成は行わない。
4. 確認可能な形式の不正行は最大2回、指定IDの行だけをLLMに修復させる。正常な行は保持し、修復応答による指定外の追加・削除・ID変更を拒否する。
5. 主体別カードを構成し、既存のカード整理・レーン表示ルールを適用した後に接続線を描く。

時刻不明の複数イベントも個別IDを持つ。同一カードにする場合は、LLMが別の共有カード表で明示する。イベント時刻の欠落だけを理由にアプリがまとめることはない。

## 2. 台帳形式

セクションは `[主体]`、`[イベント]`、`[関係]`、`[共有カード]`、`[整理]` の5つ。空でもセクションを出力する。各表の見出しは `eventLedger.ts` の `LEDGER_HEADERS` に定義する。末尾は必ず `[完了]`。

| 表 | 列 |
| --- | --- |
| 主体 | ID、名称、種類 |
| イベント | ID、時刻、見出し、内容、主体と役割、原文参照、記録区分 |
| 関係 | ID、種類、元イベント、元主体、先イベント、先主体、原文参照、リソース、実施状態、受領確認 |
| 共有カード | ID、主体、イベントID一覧 |
| 整理 | ID、区分、原文参照、要旨、理由 |

列間は実タブ、セル内のタブ・改行は禁止し、セル内改行はLLMが空白へ変換する。空値は `-`、ID一覧はカンマ区切り。IDは英字で始まる英数字・ハイフン・下線とし、セクション内で一意とする。役割は `A1:actor,A2:target` の形式。主体名や本文の句読点を区切りとして解釈しない。

種類・役割・記録区分は内部の列挙値を使う。伝達・影響では両端のイベントIDと主体IDが必要。同一イベントの複数主体は本文を繰り返さず、一つの行の役割一覧に記す。

原文参照は `p1,p2` の形式とし、原文引用を台帳に再掲しない。記録・主張・評価を区別する。背景等も原文のコピーではなく短い要旨と理由にする。アプリは参照番号から保持した原文を確認欄に表示する。

## 3. 行単位の修復と中断

修復要求には不正行、見出し、エラー、対応する原文段落、本文を含まないID一覧を渡す。主体・関係・共有カードの修復では関連イベントの参照をたどって原文を絞り、関連イベントの時刻も渡す。原文全文・前回結果全文を再送しない。参照が使えない場合は先頭の少数段落だけを補助文脈として渡し、原文番号や内容をアプリが推測して補正しない。修復で正しく対応できない場合は停止する。

主体行が不正なだけで、主体IDを正しく参照しているイベント行まで一括で修復対象にしない。共有カードの矛盾・前後関係の循環などの複数行にまたがる問題は、関係する表の行を修復対象とする。

正規化で読み取れる台帳は、失敗した修復の前後も最大3件までメモリに保持する。同じプロジェクト・モデル・接続先・入力・プロンプトで再実行すると修復から再開する。更新・アプリ終了を越えて保持する機能ではない。取得成功後はキャッシュを解放する。

ただし同じ不正行が変更なしで返った場合は修復を停止する。修復上限到達時と変更なしの停止時はキャッシュを解放し、次回は全文の正規化から再取得する。通信失敗の場合は修復再開用の台帳を保持する。

transfer/impact/mutual/commonの関係行は、両端のイベントと関与する主体IDを必須とする。LLMが原文から両端を特定できない場合は、修復対象の関係行だけを同じIDの整理review行（原文参照・要旨・理由付き）に置き換えられる。イベントは保持し、アプリ側で主体を補完しない。指定外の行、同じ関係の二重出力、既存整理IDとの衝突は拒否する。

ID重複、未知のセクション、セクション欠落、完了記号欠落など、修復する行IDを一意に特定できない応答は明示的に停止する。途中切れ・通信失敗・キャンセルを成功にせず、既存図を不完全な結果で置換しない。

背景等の再抽出は選択した記録が参照する原文を送り、その範囲の抽出済みイベントを重複防止の文脈としてLLMに渡す。新しいIDはアプリで既存IDと衝突しない名前に付け替える。出来事の同一性はLLMが判断する。

## 4. 変動判定・表示・保存・分析

変動判定もTSVで入出力する。イベント・主体と役割・記録区分・参照原文・背景をテキストで渡し、`[判定]` の4列（ID、判定、理由、原文参照）と `[完了]` を受け取る。判定の原文参照は `source_1/p1` の形式で、当該イベントの参照範囲に限定する。根拠不足は保留。欠落・不正行だけを修復し、正常な判定を保持する。

保存形式はProject 5.0／analysis 5。イベントの `sourceRefs`、`recordKind`、`classificationSourceRefs` と関係・整理記録の原文参照を保存する。新しい抽出は独立した事実一覧を作らず、内部の `facts`／`factIds` は空とする。これらのフィールドは従来の内部編集・テスト用構造のために残るが、新抽出・判定の前提ではない。保存JSONはアプリが生成し、LLMには生成させない。形式3.0以前は拒否し、変換は実装しない。

確認画面では原文段落を表示する。参照が実在しても、イベント解釈・時刻・主体が正しいことを保証するものではない。レポートにはイベントと背景の要旨を使う。変更検知には参照先原文も含める。非表示・配置だけの変更では分析内容を変えない。

## 5. 自己点検

| 確認点 | 実装・検証内容 |
| --- | --- |
| 出力の肥大化 | 独立した事実一覧・原文引用の再掲を廃止。修復も本文を含む全結果を再送しない |
| 意味判断の所在 | 正規化・イベント分離・主体・時刻・不要記述の判断はLLMへ。機械処理は取込・参照・編集整合に限定 |
| 複数出来事の圧縮 | プロンプトに個別イベント化を明記し、時刻不明の自動グループ化を停止 |
| TSVの崩れ | 列数不一致を対象行として検出。未知の形式や途中切れを黙って取り込まない |
| 修復による破壊 | 指定IDだけの置換を検証し、空応答・ID変更・無関係な行の追加を拒否 |
| 修復範囲の拡大 | 不正な主体行への参照による連鎖的な再生成を抑止 |
| 通信失敗 | 読取済み台帳を保持し、同じ条件なら修復から再開 |
| 根拠の取り違え | 不明な原文参照を拒否し、判定の範囲外参照も拒否。人が原文を確認できる |
| 保存と後続機能 | 新形式の保存再読込、変動判定、レポート、履歴・表示整理を回帰テストで確認 |

TSV化によるトークン削減率はモデルのトークナイザーに依存し、数値保証はしない。原文と事実・イベントの二重生成をなくすことが主要な削減策である。テストは通信モックによる形式・参照・復元等の確認であり、実モデルの抽出品質の保証ではない。

型チェックと全自動テストが成功した。新規・更新テストでは、原文参照付き台帳、時刻不明イベントの分離、明示グループ、関係端点、列の崩れ、ID重複・変更・追加、途中切れ、行単位の修復、修復失敗後の再開、変動判定の部分修復、形式5.0の保存再読込、原文表示、既存の配置・レーン・接続・SVGを確認した。

2026-10-29 時刻不明イベントの配置更新：analysisを持つ図では、レーン内のsequence_orderを共通の時間として扱わず、イベントIDを基準に全レーンの順位を決める。共通イベント・共有カードは同じ順位とし、明示されたbefore、impact、transferと接続の前後関係を優先する。関係がない候補はsourceOrder（入力記述順）で並べる。循環する追加制約と同一イベント間の線は時間差に変換しない。カード・接続点の中心を同じ高さへ揃え、発生時刻の文字列は補わない。保存済みの手動配置を持つ図はBT自動整列で再配置する。


## 関係台帳の検証・修復契約（2026-10-29）

現行契約は relation-attributes-2。beforeは両端イベント必須、主体省略可、リソース・実施状態は -、受領確認はna。beforeの受領確認 - も対象外として受け入れ、発生・受信の事実を補わない。既存beforeのoccurred/omitted/unknownと保存済み任意属性は互換性のため保持する。dependencyは別イベント・別主体、リソース・実施状態 -、受領確認na。transfer/impact/mutual/commonはイベントに割当済みの両端主体と有効な状態・受領値を要求する。commonは同一イベントの主体間関係として新規取込を検証する。

不正な関係はその行だけを修復対象にする。局所エラーの存在だけで別の検証可能行の意味検証を保留せず、一つの関係の意味エラーを全関係に配布しない。循環・共有カード重複は関与する辺・グループを特定する。警告には種別・列・受信値・許容値を付け、通常ログの値は長さと改行を制限する。属性規則は共通関係契約から呼び出し、旧カスタム指示へ現行契約を補足した場合はinfoで通知する。


## 未割当修復の差分契約（2026-10-29）

連鎖修復の契約はchain-delta-3。割当追加は6列（ID、イベントID、主体ID、役割、原文参照、推定表示inferred/-）、関係追加は既存12列にsource-contextを追加する。主体割当に推定理由・根拠区分は出力せず、関係根拠はrecorded/source-assessment/source-context。接続専用提案はconnection-proposal-2の14列で、従来の理由の直前に根拠区分を追加する。旧応答列数を意味推測で変換せず検証・限定修復する。

proposalContext.tsで全イベント・主体・割当・カード・関係・帰結・原文をTSV化する。原文表はref/eventIds/purpose/textの4列とし、eventIdsは全イベントのsourceRefsから逆引きする。contextは補助文脈であり、近隣イベントの実参照にはしない。割当・関係のevidenceBasis/sourceRefs/理由、割当generation、任意のentity.resolution=unresolvedを保存検証で保持する。文脈根拠には参照と理由を要求する。仮レーンは利用者作成のみで、確定操作まで診断のcompleteをfalseにする。


## 正規化の主体推定契約 subject-inference-1

イベント表の7列を維持し、主体と役割セルの通常形式ID:roleに、推定割当だけID:role:inferredを追加する。混在する複数主体はカンマ区切りとし、未知の修飾子・4要素以上は対象イベント行の形式エラーとする。推定する主体の選択自体はLLMが全文の文脈から行い、アプリは推測・直前主体の補完・型の意味推測を行わない。

VTAParticipation.inferredは任意のboolean。新しい主体推定にはreason/evidenceBasis/sourceRefsの追加提出を要求しない。イベントの原文参照は従来どおり必要であり、関係の根拠とは独立する。既存source-context割当の詳細は保持して読めるが、表示は「主体は推定」のみとする。明示inferred=falseは旧根拠区分より優先する。

組込・外部正規化プロンプトと実行時カスタム指示に同じ契約を適用し、旧主体明記制約と衝突する場合は末尾の主体推定契約を優先する。関係自体のsource-contextと根拠表示は変更しない。


## 任意監査セクションとプロンプト契約 event-ledger-13／14（2026-10-31 / 2026-11-01）

`event-ledger-13` / `event-ledger-14` では、既存の必須セクション（`[主体]`、`[イベント]`、`[関係]`、`[共有カード]`、`[整理]`、`[帰結]`）の後、`[完了]` の前に以下の任意セクションを受け付ける：

| 表 | 列 | 検証・不採用時の扱い |
| --- | --- | --- |
| 表記 | ID、種別（`alias`/`typo`）、原文表記、統一後、原文参照、理由 | 参照段落に原文表記が実在することを確認。不正行は警告を記録して当該記録行のみ除外（本体は保持） |
| 表現 | ID、原文参照、検知語句、処理（`removed`/`quoted`/`action_only`）、イベントID、理由 | 参照段落に検知語句が実在することを確認。アプリ側の辞書走査（`scanSource`）結果と統合し `normalizationAudit.subjectiveNotices` に保存 |
| 仮判定 | イベントID、判定（`normal`/`variation`/`undetermined`）、理由、原文参照 | 参照が当該イベントの `sourceRefs` 内であることを確認し `event.preliminary` に保存。`event.classification` は `unclassified` を維持 |

生成されたイベント見出し・本文に主観的評価語が含まれる場合（`claim` の引用括弧内を除く）は、`inspectLedger` が `softIssues` として返し、通常の2回修復予算内で言い換えを要求する。修復上限到達や通信失敗時は処理を停止せず、構造検証済みの台帳を採用して警告を記録する。保存データの読込（`validateSavedAnalysis`）でも、任意の監査エントリの不整合は該当エントリのみ破棄してプロジェクト読込を継続する。

### event-ledger-14 での入力トークン効率化（2026-11-01）

- **修復プロンプト（`ledgerRepairInput`）の重複送信解消**: システムプロンプトに含まれる `RELATION_CONTRACT_PROMPT` をユーザープロンプト先頭から除去し、`catalog` の不要列を省いてトークン消費を抑制。

- **接続提案候補ペアの適正化**: 作業依存候補ペアの上限を500組とし、スコープカード関連ペアを優先抽出。
