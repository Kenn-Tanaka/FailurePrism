# 結線カードのレーン間接続不足を解消する実装計画

2026-10-29。計画のみ。コード・プロンプト・配布成果物は変更しない。

同日実装進捗：全文を使うchain-delta-1の単一照会、追加主体／イベント／割当／関係／要確認の解析、差分選択・プレビュー・一括採用、関係IDによる削除照合、生成線の再投影、カードと関係の診断を追加した。照会は1回（自動修復・2パス再点検は未実装）。不正応答の行単位保持・構造化追跡、全属性を含む投影診断、診断からのカード指定起動等には計画との差が残る。以下の全項目が完了したことを意味しない。実LLMと利用者の実例の評価は未実施。

継続実装：最大2パス・修復込み6呼出し、正常行の保持と対象IDのみの修復、無進展停止、部分的な通信失敗時の候補保持、候補別の受入／除外履歴、実行ID・採用関係の来歴保存を追加した。応答全体の完了形式が不明な場合は採用を禁止する。投影診断は端点・意味に加え方向・実施／受領・リソース属性を照合する。診断パネルからのカード指定起動、割当変更・分割の自動差分化、実例と実LLMによる品質評価は引き続き未実施である。

## 1. 目的と位置付け

「結線作業の実施」が他レーンの後続作業へ接続されない問題について、原因を観測可能にし、原文に裏付けられた関係・事象・割当を差分提案して解決する。`EVENT_CHAIN_IMPLEMENTATION_PLAN.md`のT2～T7に相当する未実装部分を、接続不足の修復として一貫して完成させるための実装単位とする。

画像には結線カード下部の縦線が見えるため、「接続線が一切ない」と「同一レーン内の線はあるが他レーンとの橋がない」を区別する。保存プロジェクトと実際のLLM応答は未取得であり、今回の個別事例の原因確定・解決済みとは扱わない。

画面で全体連結を示すだけでは完了としない。根拠のない線を追加せず、関係を生成しなかった理由・採用できなかった理由・表示されない理由まで確認可能にする。

## 2. 対象ケースの期待する扱い

原文に対応がある場合の候補例は、次のとおりとする。

`旧手順による結線作業 → その結線結果を用いる通電試験 → 機器破損`

結線と他レーンの通電試験の間は、実際の物の移動がなければ「資機材移動」ではなく作業依存として提案する。通電試験と機器破損の因果を原文が明示していなければ、単に時系列で結んだことを原因の証明には使わない。

「試験前確認の完了」という見出しだけでは、結線結果を確認した事実は分からない。そのカードへの接続を固定しない。文書名が似ているだけで、総合試験手順書とサブシステムの作業手順書を同一資料として扱わない。

機器は被制御対象・被害物としてイベント本文へ残し、線を増やすための機器レーンを作らない。自律的動作を担う機器を主体にできる既存規則は維持する。帰結が未抽出・未割当なら別の不足事項として保持し、結線の関係不足と同時に点検できるようにする。

## 3. 診断を先に実装する

### 3.1 カード・成分ごとの結果

新設`connectionDiagnostics.ts`が、正規分析、実際の線、表示設定、提案処理の記録を入力に、次を返す。

| 診断コード | 条件と表示内容 |
| --- | --- |
| `no_lane_sequence` | 同一レーンの隣接線が不足。同一レーン修復の対象 |
| `no_cross_lane_bridge` | そのカードまたは同一レーンの接続経路から他レーンへ到達できず、図が分かれている |
| `no_accepted_relation` | 対象を他成分へ結ぶ採用済み意味関係がない。これだけで「LLM未生成」と断定しない |
| `order_only` | 他レーンのイベントとのbefore関係はあるが、描画する意味関係はない |
| `candidate_rejected` | 応答候補を参照・属性・循環・競合等の検証で除外した記録がある |
| `candidate_pending` | 正常候補は生成済みだが、利用者による採用待ち |
| `projection_missing` | 採用済み関係があるが、対応する描画線がない |
| `ambiguous_endpoint` | イベント・主体から端点カードを一意に解決できない |
| `user_deleted` / `display_filtered` | 利用者の削除・非表示が接続を切っている。自動復元の対象外 |

診断結果にはカード／イベント／主体／関係ID、現在の連結成分、相手候補、参照原文、根拠となった処理記録を含める。全てのカードが個別に他レーンへの直線を持つ必要はない。同一レーン内の正しい経路で他レーンへ到達できれば、そのカードは孤立とは扱わない。

単一レーンの分析では`no_cross_lane_bridge`を問題にしない。複数レーンの場合も、個々のカードに横線がないことではなく、正しい同一レーン経路を含む連結成分が分離していることを判定する。全レーンに1本ずつ横線があってもA-BとC-Dに分かれる図は未接続とする。

正規の有効グラフ、期待する投影、実際に描画されたグラフを分ける。有効グラフへ数える線は、参照・端点が有効な採用済み意味関係、同一イベントの共有関係、正しい同一レーン隣接線に限る。before、未採用候補、別イベント間の意味未判定線、参照不正線を接続済みの根拠へ数えない。利用者の明示的な意味指定はその由来を残して扱い、原文で裏付けられた関係と同一視しない。

### 3.2 提案処理の記録

既存の`invalidRows: string[]`に加え、応答内候補ID・端点・検証段階・理由コードを持つ構造化記録を追加する。形式検証、意味候補の返却、利用者の採用、描画の各段階を同じrequestIdで追跡する。

LLMが候補を返したがアプリが拒否した場合と、候補を返さなかった場合を別に表示する。過去の応答記録がない既存図については「生成時の詳細不明」とし、現在のグラフだけから過去の原因を断定しない。

応答全文・原文全文・認証情報を操作ログへ常時出力しない。画面表示用の不正行は既存どおり保持できるが、永続保存は候補・理由・原文参照・由来の必要部分に限定する。

保留中の候補と検証記録は実行スナップショットに紐付け、古い記録を現在の図の原因として流用しない。再読込後に履歴がなければ不明と表示する。採用した関係の根拠・理由・来歴と、採用せず残った要確認は保存対象とするが、未採用の提案を正規の関係表へ入れない。候補の追跡IDは`requestId + 応答内ID`、永続関係IDとは別にする。

## 4. 接続生成と投影の修正

### 4.1 beforeと意味関係

beforeは時間順だけとして保持し、描画線へ一括変換しない。`order_only`を検出した場合、LLMへ「先行イベントの成果・状態を後続作業が利用したか」を原文で確認させる。根拠があればdependency等を追加提案し、時間順しか分からなければ要確認のままにする。

初回抽出と既存図への提案に同じ関係規則を適用する。非隣接の作業依存は許可し、隣接候補一覧への掲載を前提にしない。単に最も近いカード、同じ時刻、同じ用語を選んで線を引かない。

### 4.2 投影経路

`eventAnalysis.ts`の関係投影を`projectRelations`へ分離し、全採用済み関係について、`drawn / hidden / omitted / ambiguous / invalid`の結果を返す。

生成線は安定した関係IDから再構成し、同じIDの古い端点・属性をそのまま残して再投影をスキップしない。手動編集属性・BREAK・明示削除は上書き情報として反映する。IDがない関係も他のIDなし線と同一視せず、正規データ化の境界で図の意味を変更せずにIDを確定する。診断にはIDを補った由来を残す。

ID確定をファイル保存処理の副作用にはしない。IDのない関係は読込／生成結果の正規データ化の境界で一度だけアプリがIDを割り当て、その後のプレビュー・採用・保存・Undo/Redoで維持する。診断とプレビュー中には乱数IDを再発行しない。同じ端点・種類で根拠の異なる関係を勝手に統合しない。

投影成功は線のrelationIdが存在するだけでは判定しない。対象カード、意味、方向、実施状態、受領確認、根拠となる関係IDを期待値と比較する。無向・双方向の端点比較と方向付きの比較を分ける。手動上書きは明示した属性だけに適用し、仕様上許した上書きを投影不良と誤判定しない。

ストアの変更操作に意図を持たせる。少なくとも`user-delete / semantic-adoption / projection-refresh`を区別し、再投影や意味関係の差分採用で生成線が置き換わったことを、利用者による削除履歴へ変換しない。`reconcileAnalysis`のsource/targetペアだけによる関係削除推定を改め、関係ID単位で削除・更新する。片方の平行関係を消した時にもう一方まで消す、または消した関係を復活させる処理を防ぐ。描画IDと関係IDの対応、手動上書き、削除指定を一つの適用経路で処理する。

同じカード端点に別の意味関係がある場合は、それだけで新しい関係を拒否しない。完全重複は抑止し、意味の異なる関係は別IDで保持する。手動線やBREAKの変更・置換を伴う場合だけ明示的な確認候補とし、自動上書きを禁止する。線を別々に保持しても経路やラベルが重ならないよう調整する。

表示設定で隠れている線は、意味関係を削除して描画不足を隠さない。非表示主体を介する移動を、別主体間の直接移動へつなぎ替えない。同一レーンの隣接線の必須化・飛び越し禁止は維持する。

## 5. 「連鎖不足をAIで点検」の入力と出力

### 5.1 入力

対象カードを選択できるが、修復候補の探索はそのカードに付いた段落や隣接カードだけへ限定しない。次の固定スナップショットを渡す。

1. 原文全文と全段落ID。複数資料があれば資料IDも付ける。
2. 全イベント・主体・割当、既存関係と由来、共有イベント、帰結候補、選択済み分析対象。
3. 対象カード、分離した成分、beforeのみの関係、未割当・未投影等の診断。
4. 利用者の削除・非表示・確認済み関係。復活や勝手な付け替えを禁止する。

全文を送れない場合は文字数・資料範囲を示して対象範囲の選び直しを求め、黙って切り詰めない。カードの絞り込みは調査の焦点であり、根拠資料の自動除外ではない。

新しい不足点検サービスは、既存の`proposeVTAConnections`が使う「表示イベントの参照段落＋前後段落」だけの入力作成を流用しない。非表示・未割当・整理済みのイベントと原文も入力へ含める。関係候補の総当たり一覧は不要とし、全イベントの短い一覧と対象成分を渡す。旧方式の隣接候補数上限が、新しい全文点検の実行条件として残らないようにする。

分析対象が未選択でもカードの関係不足は点検できるが、対象不明を表示する。LLMが特定の最終事象へ全てを収束させたことにはしない。

### 5.2 差分出力

既存計画の`chain-delta-1`を実装し、原文付きの追加主体・追加イベント・割当追加・関係追加・要確認を返す。旧13列の関係提案と、新しい差分提案のパーサー・操作を区別する。

今回の修復では、既存の正常なイベント・主体・関係の削除、ID変更、同名主体の自動統合は行わない。割当の付け替え・イベント分割が必要なら「修正が必要」と根拠付きで提示し、利用者の確認・既存編集後に再点検する。単なる接続候補追加では直せないと明示する。

追加候補には一時ID、元資料の参照、短い理由を必須とする。新規イベントの順序は既存イベントとのbefore等で提案し、末尾への単純追加で時系列を決めない。新規イベント・主体・割当と、それを参照する線を依存する候補群として表示する。

既に結線イベントが存在する場合、「結線済み」等への言い換えで同じ出来事を追加して接続しない。既存の全イベントIDと原文参照を入力へ渡して既存IDの再利用を指示し、重複か別の状態変化かを確定できない候補は要確認へ回す。タイトル類似だけの機械的な統合・除去はしない。

LLMに「必ず接続せよ」ではなく「関係があるか根拠を点検し、足りなければ不明を返せ」と指示する。客体の機器の主体化、別イベントの融合、未実施の送受信の捏造を禁止する。

### 5.3 実行上限

意味上の点検は最大2パス、形式修復を含め操作全体で最大6呼出しとする。2パス目は有効な差分を一時コピーへ反映した結果を使う。理由文の言い換え・ID再採番だけなら無進展として停止する。

通信失敗・上限到達・キャンセルでは、正常候補と既存図を保持する。再試行を勝手に継続しない。根拠不足で成分数が減らなくても正しい未解決結果として返し、無関係な線で成功条件を満たさない。

呼出し回数はサービスの単一カウンターで管理し、既存の形式修復ループを呼んだ結果として6回を超えないようにする。2パス目の一時コピーにある一時IDは同じ実行中で維持し、正常な1パス目候補を後の形式エラーで捨てない。利用者が再実行する場合は新しい実行として回数と来歴を区別する。

## 6. 確認画面と採用

`GraphDiagnosticsPanel`から対象カードの点検を開始できるようにし、キャンバスからも「このカードの接続を点検」を用意する。既存の「レーン間接続をAIに提案」と目的・扱える差分を区別する。

新設`ChainRepairModal`では、診断理由、原文、追加候補、修復前後の成分数、帰結までの関連、残る未解決事項を表示する。初期未選択とし、関係の意味・方向・理由を確認できるようにする。結線と試験前確認を固定ペアにせず、LLMが原文から選んだ候補を示す。

採用時は、次を一括実行する。

- プロジェクト・実行ID・意味上の内容署名が変わっていないか確認する。原文・主体・関係・削除指定の変更は失効、座標移動だけでは失効させない。
- 選択候補の依存関係を検証する。新規イベントを外したまま、そのイベントを使う線だけを採用しない。
- 永続IDを発行して一時IDを写像し、端点・参照・循環・重複・削除履歴を再検証する。
- 全選択を一時コピーへ反映し、投影と接続診断を再実行する。
- 1トランザクション・1回のUndoで反映する。手動配置・補足・接続点・BREAKを保持する。

一部だけ採用して不足が残る場合も下書きとして反映可能とする。「利用者が確認した」と「構造上つながった」と「意味上妥当と確認した」を同一の状態にしない。既存図を開いただけで再生成・自動採用しない。

検証はLLMが返した候補群全体ではなく、利用者が実際に選んだ候補群に対して行う。順序追加も含めた一括循環検査を行い、候補の並び順で結果を変えない。既存の明示beforeと依存が衝突した場合、古いbeforeを黙って消さず原文の確認事項を出す。未選択の順序修復に依存しなければ採用できない関係は、その依存も表示する。

意味署名には分析対象・帰結・全カードと割当・全関係・原文・削除指定を含める。表示設定の変更は別に追跡し、意味上の候補を再利用できても、表示プレビューは現在の表示設定で再計算する。元の手動位置をキャンセル後に上書きしない。

## 7. データ・保存・出力

Project5.0 / analysis5は維持し、候補の採用理由・関係説明・要確認・処理来歴を任意属性で追加する。既存5.0に不足があっても閲覧・編集・保存を拒否しない。旧形式の変換機能は追加しない。

診断は保存済みの成功フラグを信用せず、図の変更後・読込後に再計算する。意味上の修正をレポートの最新性判定へ反映し、座標変更だけでレポートを古くしない。診断計算だけでisDirtyやUndo履歴を増やさない。

SVG・レポートには、未実施、共通イベントの無向線、作業依存を区別して渡す。修復後も不足があれば出力にも未解決として示す。帰結が未割当で図に出ない場合、別の終端カードを帰結として代用しない。

## 8. 実装タスク

| 順序 | 対象 | 完了条件 |
| --- | --- | --- |
| R1 | `connectionDiagnostics.ts`、`graphDiagnostics.ts`、提案結果型 | カード・成分単位の未接続理由と処理段階を返す。履歴不明を未生成と断定しない |
| R2 | `eventAnalysis.ts`、`sharedEvents.ts`、`connectionProposals.ts` | 関係IDごとの投影結果、同じ端点の別関係、手動・削除・BREAKの保護を検証 |
| R3 | 新設`chainRepair.ts`、`services/generation/chainRepairService.ts`、プロンプト | 全文＋診断から`chain-delta-1`を受信。ID・根拠・依存候補・上限・無進展停止を実装 |
| R4 | 新設`ChainRepairModal`、診断パネル、キャンバス、ストア | 原文付き差分プレビュー、依存単位の選択、一括採用、失効、キャンセル、1Undo |
| R5 | 保存・下書き・Hash・SVG・レポート、仕様と試験データ | 属性・未解決状態・既存位置の保持。型検査・全テスト・build.batと配布内容確認 |

R1～R5を一連の機能として完成させる。診断だけ、プロンプトだけ、入口だけの追加を「接続不足の解消」と報告しない。新規生成方式全体の作り直しを先に終えることを前提にせず、既存の生成済み図を修復できる機能として実装する。

R2には`vtaStore.ts`の変更意図・関係ID単位の照合と、コミット後に診断結果が維持される統合試験も含める。R3は新規全文入力作成と単一呼出しカウンターを実装対象に含める。R4は「プレビューでは正しいがコミットで線が消える」ことを検出するストア経由の試験まで完了条件とする。

## 9. 受入試験

1. 結線カードに同一レーンの縦線だけがある場合、他レーンへの橋がないことを正しく表示する。
2. beforeだけがあるケースで、時間順を勝手に依存へ変換せず、原文付きの再点検候補を返す。
3. 非隣接の「結線→その結線結果を用いる通電試験」を、根拠がある場合に提案・採用・描画できる。
4. 「試験前確認完了」だけで結線検査や引継ぎを推定しない。同名に近い別資料を同一扱いしない。
5. 原文の離れた段落に依存の根拠があるケースでも、全文点検で参照できる。未送信段落の参照は拒否する。
6. 必要な試験イベントや主体割当が抜けたケースで、線だけでなく必要な追加差分を提示する。新規イベントを外した関係だけの採用は拒否する。
7. 返された候補が参照不正・循環・重複・競合で落ちた場合、カードと候補に理由を表示する。
8. 関係は採用済みなのに線がない、同じIDの古い線が残っている、端点が曖昧、別意味の線が同じ端点にあるケースを区別する。
9. 同一レーン経由で他レーンへ到達できるカードを、直接の横線がないという理由で孤立としない。A-BとC-Dの別成分は検出する。
10. 未実施の連絡や客体の機器を使って架空の接続を作らない。帰結未抽出・未割当を解決済みにしない。
11. 利用者の線削除・非表示・BREAKを無断変更せず、再点検・保存読込・Undo/Redoでも保持する。
12. 不明しか返らない場合、根拠不足として停止し、既存図と正常候補を保持する。構造上つながらないことを理由にレーンを消さない。
13. 関係IDは同じだが端点・方向が古い線を検出し、プレビュー・採用・再読込で一致するように再投影できる。
14. 同じ端点の複数関係のうち一つだけを削除し、他の関係とBREAKを保持する。意味差分の再投影によって不要な削除指定が増えない。
15. 一時IDと永続IDは安定し、プレビュー再計算・保存・Undo/Redoで変わらない。別実行が同じ候補IDを使っても混同しない。
16. 見かけの接続が別イベント間の意味未判定線だけの場合は完成とせず、単一レーンに他レーン接続を要求しない。
17. 2パスの意味点検と形式修復を組み合わせても総呼出し6回以内で停止し、正常候補を保持する。
18. 結線済み等の言い換えによる重複イベント、未選択の順序修復に依存する候補を、無条件採用しない。

固定原文・固定TSVで構造と採用を自動試験し、実LLMでは誤接続・必要関係の欠落・誤った主体化を人手照合する。実際の入力と保存JSONを取得したら、この事例を再現データとして固定する。未取得でも合成した上記ケースで実装を進めるが、「利用者の事例が解決した」とは断定しない。

実装完了時に`npm run typecheck`、`npm test`、テスト省略なしの`build.bat`を実行する。今回は文書作成のみのため実行しない。
