# レーン間接続のLLM提案機能 変更計画

2026-10-29。実装済み。計画の自己レビュー結果を反映した。

## 1. 目的と現行機能との関係

原文・確定済みイベント・主体・既存接続をLLMに確認させ、不足するレーン間の関係を提案する。候補の根拠と変更内容を利用者が確認し、選択したものだけ図へ適用する。

既存の「接続を自動修正」は同一レーンの隣接接続と同じイベントIDの表示上の連結を扱う。新機能「レーン間接続をAIに提案」は、既存のイベント間に未登録の伝達・影響がある場合や、関係未判定の線を具体化する場合を扱う。対策の排除・BREAKを提案する既存のAI対策提案とは別の操作・状態とする。

初期実装は表示中の既存カードを対象とする。同一イベントの別レーンカードと、異なるイベントの別レーンカードの両方を扱う。新しいイベント・主体の生成、主体割当の変更、カード整理、レーンの自動表示は実行しない。

## 2. 操作の流れ

1. キャンバスの「レーン間接続をAIに提案」を押す。
2. 対象となる表示カード・既存接続・参照原文を確定し、件数を示して生成を開始する。初期範囲は表示全体とし、送信量が大きい場合は表示中の選択カードとその周辺へ絞れるようにする。範囲の変更は利用者の操作で行う。
3. 処理中は進捗を表示し、キャンセルできる。正常時は1回のLLM呼出しとする。
4. 提案一覧に「接続を追加」「関係未判定の線を具体化」を表示する。各候補は初期状態では未選択とする。
5. 利用者は端点・種類・方向・実施状態・受領確認・理由・原文を確認し、必要なら候補の属性を修正する。意味や根拠が不足するものは確認事項として分け、接続候補と同じチェック操作では適用しない。
6. 選択した候補の集合全体を再検証し、一括適用する。図上の追加・変更のプレビューでは、未適用の提案であることが分かる表示にする。派生する未判定線の削除・付け替えも差分に含める。
7. 一括適用は1回のUndo/Redo対象とし、保存・下書き・SVG・レポートにも反映する。

候補0件は正常な結果として明示する。機械的に不足を必ず見つけられる機能とは説明しない。参照するイベントや主体が不足している場合は、その確認事項を表示して既存のイベント確認画面へ案内する。

プレビューは本体データと履歴を変更せず、通常の線の編集・削除・BREAK操作を受け付けない。選択0件では適用ボタンを無効にし、履歴も未保存状態も変更しない。選択集合に重複・矛盾がある場合は対象候補と理由を示し、どれを外すかアプリが勝手に選ばない。適用直前の再確認が失敗した場合は一件も変更しない。適用成功後は候補一覧を破棄し、再度の適用による重複登録を防ぐ。

## 3. 提案の意味と描画

| 種類・状態 | 提案と表示 |
| --- | --- |
| 人・物・資金・情報の移動 | 移動元から移動先へ一方向矢印 |
| 相互確認 | 確認した主体間に双方向矢印 |
| 外部事象の共通影響 | 同一イベントのカード群を無向線で表示 |
| 未実施 | 予定された元・先を属性に保持し、無向破線と未実施ラベル |
| 送信記録はあるが受信未確認 | 一方向と受信未確認を区別して表示 |
| 根拠が曖昧・方向不明 | 確認事項として表示。根拠のない別イベント間の無向線を代わりに作らない |

actor/targetという役割や、近い時刻・似た見出しだけで関係を確定しない。時系列順はリソース移動の証拠ではない。カードの存在とイベントIDの共有も、移動の証拠とは扱わない。

実施状態と受領確認は関係ごとに持つ。原文で送信が記録されていることと、相手の受信確認があることを区別する。外部同時影響が別イベントに分かれているなど、イベントの同一性自体を修正すべき候補は接続を適用せず要確認とする。

自動の無向連結は、同一イベントIDを共有するという既存の根拠がある場合に限る。別イベント間の関係の有無が不明なときは、同じ処理を流用しない。候補を利用者が修正した場合も属性・参照・選択集合を再検証し、意味や根拠を変更した場合は採用理由を更新する。LLMの当初の理由と、人が修正して採用した理由を混同しない。

## 4. LLMへの入力と出力

LLMにはJSONを生成させず、既存方式と同様のTSV台帳を用いる。

入力は次に限定する。

- 対象イベント: ID、時刻、見出し、内容、記録・主張・評価の区分、原文参照。
- 主体と関与: 主体ID・名称・種類、イベントID・役割、対応するカードID。
- 既存の線・関係: 安定したID、両端、種類、方向、リソース、実施状態、受領確認、手動編集・BREAK・関係未判定の区別。
- 表示対象、明示的な非表示・削除・採用済み関係の情報。
- 対象イベントが参照する原文段落と、保持している背景・要確認情報。段落ごとに一度だけ渡し、引用や事実一覧を重複生成しない。原文参照は複数資料でも曖昧にならない `sourceId/paragraphId` とする。

原文の範囲が足りない場合は推測して接続せず、要確認にする。初期実装では未参照の全文から新しいイベントを発掘することは目的としない。プロンプト・原文中の指示を混同しない。

原文は図のイベントに紐付くanalysis.sourcesのスナップショットを使う。利用者が後から編集した未再抽出のシナリオ本文を、既存イベントの根拠として混ぜない。対象段落と短い前後文脈の範囲を入力・原文確認画面で明示し、LLMが参照できるIDを限定する。参照範囲外の関係は確認事項として返させる。

全カードペアを事前列挙せず、イベント・関与・既存接続を線形の台帳として渡す。入力と出力に上限を設け、上限を超える場合は対象範囲の絞り込みを案内する。全文や全結果を黙って再送したり、自動的に対象範囲を変えたりしない。上限の具体値は実装・モデル設定に合わせて定め、文字数から正確なトークン数を保証しない。

応答の主表は `[接続提案]` とし、列は次の13列とする。

`ID / 操作 / 対象線ID / 種類 / 元イベント / 元主体 / 先イベント / 先主体 / 原文参照 / リソース / 実施状態 / 受領確認 / 理由`

実際の区切りはタブ。操作はadd/refine、追加時の対象線IDは `-`。種類はtransfer/impact/mutual/commonとし、beforeだけを理由に新しいレーン間の移動線を作らない。対象線IDはrefine提案を生成した時点の照合・表示情報であり、内部の適用対象は共通イベントIDと両端の主体IDで保持する。終端は `[完了]`。方向は種類と実施状態から一貫して決め、独立した矛盾する矢印指定を出力させない。必要な確認事項は別の短い `[要確認]` 表に `ID / 原文参照 / 理由` を記す。確率として解釈できないLLMの確信度パーセントは表示しない。

不正行の修復は最大2回、対象行・必要なID・原文段落だけで行い、前回結果全文を送らない。終端を持つ応答のうち、形式と参照が正常な候補は保持する。不正候補は理由とともに区別し、修復通信に失敗しても正常な候補を失わない。途中切れ・不明な応答形式は完了結果として扱わない。

候補0件、正常候補と不正候補の混在、修復通信失敗、全体の形式不正、出力途中切れを別の状態として表示する。不正候補がある応答を「不足線なし」と表示しない。正常候補の件数と適用可能な範囲を示す。ユーザーが生成をキャンセルした場合は、保持した正常候補も適用対象から外す。

## 5. 形式確認と重複・矛盾の確認

意味の判断はLLMと利用者が行い、アプリは適用可能性を確認する。

- 列数、列挙値、提案IDの重複、原文参照・イベント・主体・カードの存在。refineの対象線IDは生成時点の入力と照合し、適用時は論理的なイベント・主体ペアと現在の関係を照合する。
- 両端の主体が当該イベントに関与し、表示中の別レーンに対応カードを持つこと。複数イベントカードでもイベントIDと主体IDからカードを特定する。
- 一方向・相互確認・共通影響・未実施・受領確認の属性が矛盾しないこと。
- 自己接続、同一主体内の接続を対象外とする。異なる意味の線を端点ペアだけで重複扱いしない。
- 同じ端点・イベント・意味・リソース・状態を持つ関係の重複追加を防ぐ。無向線と双方向線は端点順を正規化して比較する。一方向線の逆向きは別の意味として扱う。
- 手動削除済みの関係、手動で変更した線、BREAK付きの線を無断で再追加・置換しない。
- 実施済みのイベント間関係が明示された前後関係と循環する場合は、矛盾候補として適用を止める。同一イベント内・無向・双方向・未実施の線を時間差の制約にしない。

上記の確認は、候補単体の段階と、利用者が選択した候補を全件加えた仮の図の両方で行う。個別には追加可能なA→BとB→Aが、同時採用で循環する場合等を検出する。同じ対象を異なる意味へ具体化する候補も競合として示す。共有カードによるイベントのグループ化も考慮し、異なるイベント間の前後関係を追加するためにカードの分割が必要になる場合は確認事項とする。カードの自動分割・イベント統合は行わない。

手動削除の既知IDだけでは、新しい関係IDでの同じ提案を検出できない。削除前に分かっているイベント・主体ペア・意味・方向・リソース・状態の照合情報も保持し、提案入力と適用時の除外判定に使う。既存の削除記録から意味が復元できない場合、分かっている対象への自動置換を避け、不明点を示す。新しいIDを発行するだけで削除指定を迂回しない。

形式・参照が正常でも意味が正しい保証にはならないため、提案理由と原文を一覧から確認できるようにする。

## 6. 追加と具体化の適用

addではアプリが新しい安定した関係IDを発行し、元の提案ID、提案理由、採用理由、原文参照、LLM提案を利用者が採用した由来を記録する。候補を手動修正したかも区別する。イベントの変動判定や対策指定は変更しない。

refineの対象は、自動生成された関係未判定の共通イベントグループに属する主体ペアに限定する。採用時に意味上の関係を追加し、接続生成を通じて表示用の未判定線を具体的な線へ置き換える。列順変更で中間の描画区間が変わっても、同じイベント・主体ペアの提案の意味は変えない。既存の実関係線や手動編集・BREAK付き線を自動的にrefineしない。これらと競合する提案は要確認として区別する。

適用前後の差分を提示し、選択していない候補を反映しない。補足・グループ注記・既存の関係IDと線ID・手動の位置を維持する。新しい線は既存位置を結び、配置を変更する場合は利用者がBT自動整列を実行する。3主体以上は明示された主体ペアごとに提案する。

選択した意味上の関係を追加した結果として、表示用の未判定線が不要になったり連結区間が変わったりすることはある。その派生変更もプレビューと履歴に含めるが、未選択の意味上の関係を採用したことにはしない。

関係の保存後に既存のprojectAnalysis/connectSharedEventsから描画を作る。表示上のエッジだけを追加して、再表示・再描画で消える実装にはしない。採用した関係の端点は、次の自動整理で必要なカードとして保護する。

適用処理では「利用者が線を削除したこと」と「未判定線が派生データとして置き換わったこと」を区別する。後者をomittedEdges等の手動削除記録へ追加しない。現行commitVTAChangeは消えた生成線を削除指定として保存するため、適用コマンドまたはコミット情報で理由を区別する変更を含める。描画前後の結果から削除理由を推測しない。

プレビューと本適用は同じ選択集合の適用計画・接続生成処理を使う。追加する関係・保持する関係・派生線の変化・保存する由来を含む計画を一括でコミットし、途中だけ保存される状態を作らない。適用後は新規提案としての保留状態から利用者が確定した関係へ移し、後の生成で無断上書きされないようにする。

## 7. 古い提案の適用防止と保存

生成開始時にプロジェクトID・要求ID・提案入力の署名を記録する。生成中と採用前の両方で照合する。プロジェクト切替、再抽出、イベント・割当・線・原文・表示対象の変更後は古い提案を適用せず、再提案を案内する。

既存の分析用ハッシュは表示設定を意図的に含めないため、提案用の入力署名を別途持つ。署名には原文、イベント、主体、関与、関係、意味を持つ線・手動上書き・削除、表示カード集合を含める。表示用の未判定線は変動する線分IDをそのまま署名にせず、イベントIDと参加主体集合で表す。単なるパン・ズーム・座標移動・列順変更では候補を失効させず、現在の位置でプレビューを描き直す。ストアのオブジェクト参照が変わったことだけでは失効させない。

生成するデータとプロンプトは開始時点のスナップショットを使う。修復も同じスナップショットに対して行い、途中で変わった最新図の一部を混ぜない。図の意味が変わった後に返った応答は適用可能な提案として扱わない。初期実装では抽出・変動判定・レポート・対策提案等とのLLM操作を同時実行させず、要求ID・中断処理・進捗表示の取り合いを防ぐ。

候補は作業中の一時状態とし、キャンセル・プロジェクト置換で破棄する。採用した関係と由来・理由・原文参照だけをプロジェクトへ保存する。保存用JSONはアプリが生成する。既存形式5.0への任意属性の追加で対応できるか実装時に確認し、必須契約が変わる場合のみ版を更新する。旧形式の変換機能は実装しない。

保存契約への追加は型だけで完了としない。保存検証・読み込み・編集反映の明示的な属性コピーに、由来・提案理由・採用理由を含める。未適用の候補・通信状態は永続化しない。実関係の採用は分析用ハッシュにも反映し、表示の具体化だけを理由にレポートの再生成を見落とさないようにする。

## 8. 実装対象と順序

| 対象 | 変更 |
| --- | --- |
| types/vta.ts | 提案行・状態・採用由来の型を追加 |
| services/llm | connectionProposalプロンプト、TSV入出力、原文の集約、行修復、キャンセル |
| 新規の接続提案ユーティリティ | 参照・重複・候補間矛盾確認、論理グループに対するadd/refine差分、入力署名、選択集合の適用計画 |
| vtaStore.ts | 提案専用の進捗・候補・要求ガード、派生線置換と手動削除の区別、削除対象の意味の記録、1回のUndoでの適用 |
| VTACanvas・新規提案モーダル | 起動ボタン、未適用プレビュー、一覧選択、原文確認、0件・部分不正・失効表示 |
| eventAnalysis/sharedEvents | 採用関係からの再投影、未判定線の置換、手動属性の保持 |
| 保存・レポート・SVG・文書 | 採用関係の永続化、根拠と意味の引継ぎ、利用手順 |

順序はデータ契約・署名 → TSV処理 → 提案確認・適用計画 → ストアとUI → 保存・描画・文書 → 全検証とする。既存の機械的な接続修正とAI対策提案は別操作として維持する。

## 9. 受入条件と自己点検項目

- 別イベント間の不足線を提案でき、共通イベントの無向線も具体化できる。
- 人・物・資金・情報、相互確認、共通影響、未実施、受信未確認を区別する。
- 根拠不足、存在しない参照、未割当主体、非表示・削除済みの対象を勝手に適用しない。
- 同じカードペアに複数の意味があっても別の線を更新・削除しない。逆方向の同一無向関係は重複しない。
- 未選択の候補・既存の手動線・BREAK・補足・位置を保持し、適用を1回のUndo/Redoで戻せる。
- 適用後に再提案・再描画しても重複せず、保存再読込・下書き・非表示からの復元・SVGで採用関係を維持する。
- 新しい入力への切替、表示対象変更、生成キャンセル、遅れて返った応答、提案表示後の編集に対する失効を確認する。
- 空候補、不正行、部分修復失敗、途中切れ、HTTP 504を区別し、途中結果で既存図を置換しない。
- LLMの通信モックによる検証と、実モデルでの抽出・提案品質の評価を分けて報告する。

追加で、候補単体では正常でも同時採用で循環・重複するケース、refine後に未判定線の置換が手動削除として残らないこと、列順変更でrefine対象の描画区間が変わるケース、異なる資料の同じ段落番号、採用理由の保存復元、シナリオ本文だけを編集した未再抽出状態、選択0件・適用失敗時に履歴を作らないことを確認する。

実装完了前にnpm run typecheckとnpm testを実行する。配布成果物を更新する際はbuild.batをテスト省略なしで実行し、起動用distと配布版に機能が反映されることを確認する。

| 重要度 | 見つかった問題 | 修正方針 |
| --- | --- | --- |
| 高 | 個々の候補が正常でも、まとめて採用すると循環・重複・具体化の競合が起こる | 選択集合と既存図を組み合わせて再検証し、一括で適用／中止する |
| 高 | refineで消えた生成線が、現行コミット処理により手動削除として保存される可能性がある | 意味上の追加と派生線の再構成を区別し、削除理由を明示する |
| 高 | 列順変更で生成線のID・端点が変わることと、提案を失効させない方針が矛盾する | refineをイベント・主体ペアで保持し、署名には論理グループを使う |
| 高 | 根拠不十分な別イベント間の候補に無向線を付けると、未確認の関係が実在するように見える | 確認事項へ分離し、同一イベントの無向連結と混同しない |
| 高 | 削除済み線を新しいIDで提案すると、IDだけの除外をすり抜ける | 分かっている削除対象の意味も照合し、自動的に再追加しない |
| 中 | 後で編集したシナリオ本文と確定済み図の原文が混ざる可能性がある | analysis.sourcesの同じスナップショットから入力と修復文脈を作る |
| 中 | 不正候補や修復通信失敗を候補0件と混同すると、正常候補を失う | 正常・不正・未完了・0件を別状態にし、正常候補を保持する |
| 中 | 由来や理由のフィールドを型だけに追加すると保存検証で消える | 検証・保存・読込・編集反映を更新し、往復テストを行う |
| 中 | 他のLLM機能と要求ID・中断・進捗を共用すると別処理の結果が混ざる | 同時実行を制限し、要求とスナップショットを一貫して照合する |
| 中 | 大きな図で入出力が膨らみ、従来の長文タイムアウトを繰り返す | 全ペア列挙を避け、原文を重複排除し、明示した範囲と上限で扱う |

修正後の計画は実装可能と判断する。意味の妥当性はLLMと人による確認に残し、機械処理は取込・参照・選択集合・更新の整合性を扱う。
