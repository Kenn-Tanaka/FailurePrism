# 事象の連鎖を中心とするVTA図生成 修正計画

2026-10-29。計画段階。コード・プロンプト・配布成果物には未反映。

具体的な契約・実装順序・試験と自己レビューは[具体的実装計画](EVENT_CHAIN_IMPLEMENTATION_PLAN.md)を参照。同計画では、確認状態と完成状態の分離、分析対象の確認後に行う不足点検、操作全体のLLM呼出し上限を補強している。

## 2. 現行方式の問題

問題はプロンプトの一文だけではない。抽出から表示までの設計が、局所的に正しい候補が得られれば十分という構造になっている。

1. `eventPrompts.ts`はイベントと主体を抽出するが、分析対象の最終事象、各レーンと最終事象との関係、未解決の連鎖を明示的に管理していない。
2. `eventOrder.ts`の`dependencyCandidates`は対象2主体の隣接イベント以外を候補にしない。原文上は関係があっても、その間に別作業があれば依存を提案できない。
3. `sharedEvents.ts`は同じイベントIDを持つカード群を接続する。別IDの実際の工程間関係が抜けても、図全体が連結することは保証しない。
4. `connectionProposals.ts`は個々の参照・属性・循環・重複を調べるが、孤立レーン、複数の連結成分、最終事象との関係の欠落は調べない。
5. `presentation.ts`の単独カード整理により、唯一の他レーンとの接点を表示から外し得る。`visibleSchema`は非表示ノードの両端にある線を除くので、正規データでの連結と表示図の連結も一致しない。
6. `eventAnalysis.ts`では、同じカード端点の線があると別の意味の関係の投影を省く分岐がある。同一イベントのまとまり、工程上の依存、実際のリソース移動を一律に端点ペアで扱えない。
7. 「参照先が存在する」「TSVが正しい」「テストが通る」は、VTAとして必要な連鎖が抽出できた証拠ではない。実資料に基づく意味上の受入条件が不足していた。

リポジトリ内のサンプル`sample-project.vta.json`は「担当者が装置を起動→装置停止」の小例であり、担当者の単独カードは表示整理の対象になっている。保存データだけからは、利用者が今回観測した孤立レーンの実例と同一とは確認できない。今回の個別事例の原因断定と、上記の構造的な不足の確認は分ける。

## 3. 変更する原則

### 3.1 図全体を先に構成する

原文から「分析対象の不具合／事故」「対象期間・範囲」「関連主体」「事象」「事象間の関係」を一体で整理する。必要な通常作業・状態・未実施を含む連鎖を作り、その投影としてカードとレーンを構成する。

分析対象は単に時刻が最後のイベントを選ばない。事故後の救助や調査を含む資料では、分析対象の衝突と、その後の脱出・消火を区別する。最終事象の候補と根拠を示して利用者が確認・変更できるようにする。複数の独立した事故が混在する場合は分析範囲の分割を提案し、架空の共通最終事象を置かない。

最終事象を起点とする逆向きの点検は、必要な工程を見落とさないために使う。最初から特定の原因を選んで他の情報を排除する用途には使わない。生成スキームが分析範囲外と判断した記述も、原文参照・要旨・理由を保持して利用者が戻せるようにする。

### 3.2 レーン間の隣接制限を撤回する

**同一レーン内**の時系列接続は、従来どおり隣接ノード間を必ず結び、中間ノードを飛び越えない。

**異なるレーン間**では、根拠があるリソース移動・作業依存・影響は、時系列上隣接していなくても接続できるようにする。対象2レーン内に別の作業があっても、それだけで依存を否定しない。隣接性は優先して点検する候補の手掛かりに留め、採用の必須条件から外す。

この変更は前計画`WORK_DEPENDENCY_CONNECTION_PLAN.md`の隣接限定規則、およびそれを「全方式共通の必須条件」とした部分を置き換える。実装承認後、要件定義・実装仕様・プロンプト・テストを同時に改訂する。変更は既存の依存線の削除理由にしない。

### 3.3 線の意味を混同しない

| 関係 | 表現と制約 |
| --- | --- |
| 同一レーンの時間的連続 | 隣接ノード間の時系列線。因果関係の断定には使わない |
| 実際のリソース移動 | 移動元から移動先への矢印。送信の記録だけで受信済みとしない |
| 相互確認 | 根拠のある主体間だけ双方向矢印 |
| 外部事象の共通影響 | 共通イベントのカード群を無向で接続。主体間の移動を意味しない |
| 作業依存 | 前提作業から依存作業へ「作業依存」の矢印。非隣接も許可 |
| 連絡・反映・作業の未実施 | 未実施を保持し、存在しない実行・受領を矢印で示さない。確認できた予定関係や、その未実施状態を前提に進んだ後続作業を個別に根拠付ける |
| 関係が不明 | 不明として診断・欄外に残す。別イベント間を「関係未判定」の線で強制接続しない |

同じイベントIDのカードを接続する現行規則は維持するが、接続を作る目的で別の出来事を同一IDに統合したり、イベントを他レーンへ根拠なく複製したりしない。通常事象／変動要因の分類は、イベント・主体・関係の確認後に行う。

## 4. 完成条件と不足状態

「各レーンに他レーンへの線が1本ある」だけでは、A-BとC-Dという二つの島を見逃す。次の条件を分けて検証する。

### 4.1 正規データの構造検査

- 対象は分析範囲に含める全ての非空レーンと、そのノード・接続点。空の手動追加レーンは構造上の孤立とは別に通知する。
- 複数レーンの図では、各レーンに意味または共有イベントの同一性で裏付けられた他レーンとの接続があること。
- レーンを頂点にした無向グラフだけでなく、全ノードと有効な線の無向グラフでも連結成分が一つであること。同一レーンの途中分断も検出する。
- その連結成分に、確認済みの分析対象事象が含まれること。単一レーンの場合は他レーン接続を要求しない。
- 時系列線による構造上の到達と、意味を持つ関係による分析対象への関連を区別して示す。連結であっても全ての線を原因とみなさない。
- リソースの双方向性や同一イベント内の相互確認を時間的循環としない。イベント発生単位の前後関係の矛盾を別検査にする。

### 4.2 表示図の検査

表示する非空レーンのノード・接続点で、表示上の連結成分を再計算する。接続点として表示するノードは通常ノードと同様に頂点に含める。

正規データで連結していても、利用者がレーン非表示・線削除をした結果として表示が分かれていれば「表示操作による分断」とする。ユーザー指定を無断解除せず、復元候補と理由を示す。非表示主体を経由した線を、別主体間の直接のリソース移動へ置き換えない。

初期の自動整理は、全関係を組み立てた後に実行する。整理前後の連結性と共有イベントの代表を比較し、唯一の接点や主体の関与を損なうカードは残す。自動整理でレーンが丸ごと消える場合は、分析対象に必要な主体かを確認対象とし、単独重複カードという理由だけで消さない。

### 4.3 状態と操作

生成結果は「確認待ち」「構造上の不足あり」「利用者確認済み」に分ける。連結性合格だけで意味の正しさまで検証済みと表示しない。

根拠が足りず孤立を解消できない場合は、イベント・正常な関係・原文を保持し、孤立レーン／連結成分と不足情報を示す。**不足を隠す接続・削除・非表示を行わず、完成したVTAとして扱わない。**追加資料、関係の手動確認、分析範囲の変更で解決する。

下書きの保存・編集・閲覧は可能とする。SVGとレポート生成時には構造上の不足を確認でき、未解決のまま出力する場合は不足状態を出力に記録する。連結性だけを満たすために正常データを消す実装にはしない。

## 5. 新しい生成フロー

### A. 分析範囲と全文スナップショット

原文、モデル、実効プロンプト、方式・ルールの版を固定する。分析対象の最終事象と範囲を指定できるようにし、未指定ならLLMが根拠付きの候補を返して利用者確認に回す。

### B. LLMによる全文からの連鎖構成

長いコンテキストに対応するモデルを前提に、初回は全文を1パスで読み、以下を簡潔なTSV台帳へ変換する。

- 個別イベント、通常作業・状態・未実施、原文の時刻と順序。
- 分析対象との関連を持つ主体と、その役割・関与。
- 同一イベントの共有と、別イベント間のリソース移動・依存・影響。
- 関係ごとの原文参照、短い説明、実施／未実施／不明、受領確認。
- 背景・前提条件、範囲外候補、矛盾・不足・要確認。

カードごとに独立した短い文章を生成するだけで終えず、「どの連鎖に、どの根拠で参加しているか」を全文で点検させる。LLMに無条件の全レーン接続を命令しない。根拠不足を出力できる契約にする。複数イベントを1カードへ畳んで連結問題を回避しない。

### C. アプリによる共通検証と不足診断

アプリは型、ID、送信済み原文参照、関係属性、循環、重複、全体の連結成分を検証する。原文の意味、因果・依存の実在性、自由記述の時刻はLLMと利用者が判断する。意味をキーワードや座標から決定する処理には置き換えない。

不足診断は「未抽出」「主体割当不足」「関係不足」「要確認関係」「表示整理による切断」「ユーザーの非表示・削除」「投影失敗」に分ける。確定した原因と、追加確認が必要な推定を区別する。レーン名・イベント・関係・原文・成分を確認画面から辿れるようにする。

### D. 必要な場合だけLLMによる不足再点検

構造上の不足がある場合、孤立した成分、分析対象、既存の確定関係を原文とともに渡して、不足している関係・イベント・主体割当を再点検する。孤立成分に付いた段落の前後だけでは遠隔の記述を見落とすため、初回の全文スナップショットを原則として再利用する。上限超過時は対象範囲を利用者に示し、黙って切り詰めない。

既存図の修正では、イベント追加・割当変更・関係追加を差分提案として返す。正常なイベントの削除・ID変更・融合は禁止し、必要な変更は原文と理由付きで別途提案する。新規イベントにはアプリが永続IDを割り当てる。

有効な構造修復は最大2回、進展がなければ停止し、要確認へ戻す。形式修復と連鎖の不足点検は別の試行回数・ログとする。際限のない再生成や、成功するまで全体を捨てる再試行をしない。

### E. 確認・整理・再検査・反映

利用者が最終事象、レーンの採用範囲、追加・変更候補、未解決事項を確認する。承認後、連結性を保つカード整理、同一レーンの隣接線、意味上のレーン間線、共有イベントの表示線を一貫した処理で投影する。

投影の後にも検査し、正規関係が表示線へ変換されなかった場合は関係IDを示す。複数の意味を同じ端点ペアという理由で捨てない。意味の異なる関係はID単位に保持し、経路・ラベルを調整する。

最終結果と診断を一括反映し、1回のUndo/Redoで戻せるようにする。手動配置・カード属性・BREAKを保持し、配置の再計算は明示操作とする。

## 6. 生成方式・データ契約

前回追加した共通入口を利用し、新方式を`event-chain`として実装する。既存の`fulltext-ledger`は比較・検証のために残す。方式選択UIは実装済みの2方式だけを表示し、新規生成の既定をevent-chainとする。既存図を開いたときに自動再生成しない。

方式の成果物には、分析対象ID・分析範囲・関係の説明・要確認事項を持たせる。連結成分などの診断は共通サービスで算出する。保存した「連結済み」フラグを信用せず、読込後・編集後・表示変更後に再評価する。

モデルが付けた自己評価、アプリが確認した参照整合性、利用者の確認状態を別属性にする。共通の完成条件は方式によって迂回できないが、未完成データの閲覧・保存を拒否する条件にはしない。

プロジェクト5.0へ追加する項目は任意項目を基本とし、既存5.0の正常なイベント・関係・座標を維持して読める設計とする。分析対象未設定・来歴不明は、その状態で読み込み、利用者に設定を求める。今のデータを機械的に別のイベントへ変換する機能、5.0より前の形式の変換は追加しない。意味や必須構造を破壊する変更が必要になった場合は保存版を上げ、その判断を実装前のデータ契約確定で明示する。

台帳は引き続きTSVとし、必要な分析範囲・関係説明・要確認の列／セクションだけを拡張する。通常の全文抽出・限定形式修復・既存図への差分提案の契約を区別し、正常な行の再生成を抑える。旧カスタムプロンプトを黙って新契約として実行せず、対応版を確認し、更新が必要な場合は画面に示す。

既存の自動修正ボタンは、同一レーン接続の修復と、図全体の不足点検を区別して表示する。前者だけを実行したことをもって「VTA全体を修正済み」としない。

## 8. 受入条件

1. 各レーンの接続本数が1以上でもA-BとC-Dに分かれた図を、複数成分として検出する。
2. 最終事象を含む一つの成分に、分析範囲内の全非空レーン・全ノード・接続点が含まれることを確認できる。
3. 間に他作業がある「手順書作成→その手順書を使用する結線」の原文付きレーン間依存を許可する。同一レーンの飛び越し線は禁止したままとする。
4. 単なる時系列の近さ、同じ単語、一般知識、無関係な同時発生から線を生成しない。接続のためにイベントを融合・複製しない。
5. 通知未実施・仕様未反映・受信未確認を含む事例で、未実施を通常の伝達へ変えず、原文にある後続作業との関係を確認できる。
6. 内容をまとめ過ぎたイベント、割当漏れ、欠けた通常作業が原因の場合、関係追加だけで解決済みにせず、対象差分を提示する。
7. 単独カード整理が唯一の接点を消す場合はそのカードを残し、ユーザーのレーン非表示・線削除による分断は無断復元しない。
8. 同じ端点に異なる意味の関係があっても、関係IDと原文を保持し、投影を黙って省略しない。
9. 根拠不足で接続できない例は未完成として保持する。架空の関係、勝手なレーン非表示、偽の共通最終事象で合格にしない。
10. 原文に事故後の救助・調査が含まれても、最終時刻だけから分析対象を誤設定しない。複数の独立事故は分割候補を出す。
11. 小サンプル、利用者の実際の孤立事例、非隣接依存、複数成分、複数の独立事故、単一レーン、空レーンを回帰データに含める。実際の孤立事例は入力・保存結果を入手後に固定する。
12. モック応答で構造・限定修復・保存・履歴を試験し、実LLMではレーン・事象・関係の正しさを人手で原文照合する。接続率100%だけを品質指標にしない。

実LLMの評価は、誤接続、必要関係の欠落、未実施の誤解釈、イベント融合、必要レーンの脱落、原文にない追加を含めて記録する。根拠がある標準例で全体連結を満たすことと、根拠不足例で無理に連結しないことを両方の合格条件とする。モデル・プロンプト・生成方式の版も記録する。

実装完了時は`npm run typecheck`、`npm test`、テスト省略なしの`build.bat`を実行する。今回の計画作成では実装・実LLM通信・ビルドは行わない。

## 9. 計画の自己点検

- 資料の事実と製品固有の完成条件を分けた。抜粋外の規則は推定して引用しない。
- 「全レーンに線を追加」という命令だけではなく、分析範囲・連鎖構成・構造診断・不足修復・表示整理を見直す。
- 前回のレーン間隣接限定は明示的に置き換え、同一レーンの規則まで撤回しない。
- 連結性は決定論的な構造検査であり、意味の生成はLLMが担当する。利用者が希望したテキスト変換中心の方式を維持する。
- 全体連結を保証できない資料では、未完成状態を正直に返す。根拠に忠実であることと、強制的な見かけの連結を両立できるとは扱わない。
- 新方式を共通入口へ追加し、過去の方式・保存図を無断で置換しない。
