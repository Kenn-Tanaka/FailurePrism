# レジリエンス分析プロンプト Ver.2.3
## このプロンプトの目的

事故・インシデントを分析する際、通常は
「誰が悪かったか」「どこでミスしたか」を探しがちです。

しかし、このプロンプトは**2つの問い**を同時に立てます：

> **❶「なぜ今まで（ほぼ）うまくいっていたのか？」**
> ── 通常運転を支えていた適応・工夫・調整を可視化する
>
> **❷「前提が崩れたとき、何がうまくいかなくなったのか？」**
> ── ❶で見えた適応能力が、なぜ今回機能しなかったかを問う

Safety-IIの立場では、❶なしに❷を問うことは
「人間の失敗を探す作業」に逆戻りします。
**必ず❶から始めてください。**

---

## 【重要】分析にあたっての入力制約（必ず守ること）

* この分析は、**提供された資料・記録・ログのみに依拠**する
* 資料に明示されていない事柄を【事実】として断定してはならない
* 判断できない場合は、無理に補わず **「不明」** と記述する
* もっともらしさよりも、**検証可能性・出典の明確さ**を優先する

---

## 基本原則（分析を始める前に読んでください）

### ❶ 責任追及が目的ではありません

* 「誰が悪いか」を探す分析は禁止
* 「なぜ破局を防げなかった構造になっていたか」を探ります

### ❷ 人間の間違いは「通常運転」です

* 判断ミス・ルール逸脱・勘違いは**起こる前提**
* 問題は、それが即破局につながる**設計・運用構造**です

### ❸ 時間軸を最優先します

* いつ気づけたか
* どれくらい猶予があったか
* なぜその時間窓が使われなかったか

### ❹ 「成功」は分析に値します

Safety-IIでは、事故が起きなかった日々の運転こそが分析対象です。

* 「普段どう乗り越えていたか」を問わずに「今回なぜ失敗したか」を問うことは禁止
* 作業者の適応・工夫・即興判断を「ルール違反」として扱わないこと
* システムの成功は「人が正しく行動したから」ではなく「構造が成功を支えていたから」と捉えること

---

## 分析の6ステップ

---

## 問0（必須）：なぜ今まで大事故にならなかったのか？

Safety-IIの出発点は「失敗の分析」ではなく**「成功の分析」**です。
問1以降に進む前に、必ずこの問いに答えてください。

### 書くべきこと

同種の作業・状況が過去に繰り返されてきた中で、
なぜ事故に至らなかったのかを分析してください。

以下の3点を記述すること：

---

### ① 通常運転を支えていた「見えない調整」

作業者・オペレーターが明文化されていないルールや
暗黙の工夫で補っていた箇所を列挙する。
（例：「熟練者が非公式に圧力確認を追加していた」など）

【記述タグ】：【事実】【推定】【仮説】を厳格に使用

---

### ② 今回「初めて重なった」条件は何か

過去の成功と今回の失敗を分けた差分条件を特定する。
「今まで起きなかったこと」ではなく
「今回だけ揃ってしまったこと」として記述する。

---

### ③ 作業者が「合理的にそう判断した」理由

ルール違反・判断ミスに見える行動について、
その時点の情報・文脈・制約の中では
なぜそれが合理的選択に見えたかを記述する。

⚠️ 注意：「なぜミスをしたか」を問うのではなく、
「その状況でその判断をした人間を、
 別の人間に替えても同じ判断をしたか」を問うこと。

---

### 📌 記述ルール：タグの厳格運用

すべての記述の冒頭に、以下のタグを付けてください。

| タグ       | 定義                                |
| -------- | --------------------------------- |
| **【事実】** | 一次資料に同趣旨の明示的記述があり、出典（p/節/時刻等）を示せる |
| **【推定】** | 直前に列挙した【事実】から合理的に導ける解釈            |
| **【仮説】** | 可能性の一つに過ぎず、現時点では裏付けがない            |

#### 追加ルール（重要）

* 【事実】には必ず出典を付ける
* 【推定】を書く場合、**根拠となる【事実】を最低1つ併記**する
* 【仮説】を書く場合、**「反証可能性（確認すべき追加データ）」を1行添える**
* 心理状態・バイアス語（正常性バイアス等）は、証拠なしに【事実】として書かない

---

## 問1：何が想定外だったか？

### 書くべきこと

事故の背景には、
**「これは起こらない」「考えなくてよい」**とされていた前提があります。

それを **3〜5個**、箇条書きで列挙してください。

各前提について、以下を書くこと：

---

### ① その前提は何だったか？

（具体的・運用レベルで）

### ② なぜそう思われていたか？

（過去実績・規程・慣行など）

### ③ 実際には何が起きたか？

（前提がどう崩れたか）

### ④ 前提が崩れた背景に、日常運用の圧力・最適化はなかったか？

（時間・手間・顧客影響・定時性など）

**④を書く際の注意点：**
* 単なる推測で終わらせず、**資料から読み取れる運用上の制約条件**を根拠にすること
* 可能であれば、時系列データから**前提が崩れていた期間の長さ**を明示すること
* 例：「【事実】○月○日から△月△日まで約X日間、アカウントが放置されていた」→「【推定】この期間、定期的な棚卸しプロセスが機能していなかったと考えられる」

---

## 問2：システムはどう反応したか？

想定外が起きたとき、
**システム（人＋機械＋組織）はどう振る舞ったか**を、時間軸で評価します。

---

### ステップ1：時間を区切る

出来事を **3〜5フェーズ** に分けてください。

```
フェーズ1：異常の初期検知（時刻）
フェーズ2：専門家介入（時刻〜）
フェーズ3：引き継ぎ・判断継続（時刻〜）
フェーズ4：停止・収束
```

---

### ステップ2：各フェーズを評価する

⚠️ **Safety-IIの原則：**
各フェーズを評価する前に、
「同じフェーズが通常運転でどう処理されていたか」を
先に記述してください。
差分が見えて初めて「何が機能しなかったか」が分かります。

以下の表を埋めてください。

| 評価項目        | 評価内容                  |
| ----------- | --------------------- |
| **通常時との差分** | 同フェーズで通常運転時はどう振る舞っていたか。今回何が違ったか |
| **システムの反応** | 柔軟だったか／硬直していたか（具体行動で） |
| **被害の広がり**  | 局所→拡大のどこにいたか          |
| **介入の余地**   | 時間窓はあったか／なぜ使われなかったか   |
| **検知シグナル**  | 本来見えるべきだった異常・前提崩壊の兆候  |
| **根拠（出典）**  | 報告書p/節/時刻・ログ・証言       |
| **確度**      | 高／中／低                 |

※ 評価語だけで終わらせず、**必ず具体的行動・判断を書くこと**

**介入の余地を評価する際の追加観点：**
* 時間窓が存在した場合、**その長さを定量的に示す**こと
* 時間窓が使われなかった理由を、以下の観点で分析すること：
  * **検知の失敗**：シグナルが見えなかった／見過ごされた
  * **判断の失敗**：シグナルは見えたが重要性を認識できなかった
  * **対応の失敗**：重要性は認識したが対応手段がなかった／優先順位が低かった

---

## 問3：段階的に悪化を防げなかったか？

### ❶ どこが「All or Nothing」だったか

* 成功 or 失敗の二択になっていた判断・設計はどこか
* 中間状態を許さなかった箇所はどこか

**❶を書く際の注意点：**
* 単に「二択だった」と指摘するだけでなく、**欠落していた中間層を具体的に列挙**すること

**記述例（化学プラントの例）：**

```
圧力制御システム：
【事実】設定圧力を超えたら即座に緊急停止する設計。
【欠落していた中間層】
  - 段階的な圧力リリーフ（低圧弁→中圧弁→高圧弁）
  - 警報による操作員への通知と手動介入の余地
  - 原料供給の段階的削減
```

---

### ❷ どこで劣化・縮退させられたか

```
【通常運転】→【要注意／制限モード】→【完全停止】
                  ↑
              ここで止められた
```

---

### ❸ 縮退モードの仕様書を書く（必須）

**基本フォーマット：**

```
【縮退モード名】：○○モード

1. 発動トリガー（何を検知したら発動するか）
2. 制限内容（通常運転と比べて何を制限するか）
3. 通知・ログ（誰に何を伝えるか）
4. 解除条件（どうなったら通常に戻すか）
5. フォールバック（制限による業務・プロセスへの影響をどう緩和するか）
6. 誤作動・濫用を防ぐガードレール
```

※ 数値・条件を書く場合は「なぜその設定か」を一言添えること

**各項目の詳細要件：**

**1. 発動トリガー：**
* 定量的な閾値を示す
* なぜその閾値か、根拠を一言添える
* **人の判断に依存するトリガーの場合、それをDCS等で自動検知・記録できないか検討すること**（MOC：Management of Changeとの連動を考慮）

**3. 通知・ログ：**
* アラートの重要度分類（高/中/低）を明示
* エスカレーション基準を含める

**4. 解除条件：**
* 解除前の確認事項を具体的に列挙
* 解除権限者を明確化（役職名まで）
* **一時的な状態変化（例：ガス濃度の瞬間的低下）を解除条件にしないこと**。複数箇所・複数回・一定時間の継続確認を要件とすること

**6. 誤作動・濫用を防ぐガードレール：**
* 監査ログの保存期間と確認頻度を明示

---

### ❹ 根本的な設計変更案

* 運用改善ではなく **仕組み自体を変える案**
* **最小実装（短期）／拡張（中長期）**の2段で記述
* 既存技術で実現可能な範囲を意識する

**記述時の注意：**
* 各提案の**優先順位と根拠**を明示する
* コスト・ロードマップは**資料に根拠がある場合のみ**記述
* 推定で書く場合は【推定】タグを付け、「一般的な○○分野では」等と注釈を加える

```
【最小実装（短期）】
- 提案1（優先度：最高／高／中、効果：高／中／低、コスト：高／中／低）
- 提案2...

【拡張（中長期）】
- 提案3...
```

---

## 問4：レジリエンスの4能力はどこで発揮され、どこで限界に達したか？

### ⚠️ 重要な前提

4能力は「あるかないか」の二値ではありません。
通常運転では機能していた能力が、
今回の条件下で限界に達した、という見方をしてください。

「○○能力が欠けていた」という表現は禁止です。
「○○能力は△△という形で発揮されていたが、
 □□という条件が重なったとき限界に達した」
という形式で記述してください。

| 能力 | 通常運転での発揮状況 | 今回の限界点 | 限界に至った条件 |
|------|------------------|------------|--------------|
| **予測**：将来のリスクを見通す | | | |
| **監視**：今何が起きているか把握する | | | |
| **対応**：異常に素早く対処する | | | |
| **学習**：過去から教訓を得る | | | |

### 能力間の相互関係を明示すること

各能力の限界が、次の能力の限界を引き起こす連鎖を分析する。

```
【能力間の相互作用】

例：
予測の限界（非定常状態を通常と区別できなかった）
　↓
監視の限界（監視対象に非定常条件を含めていなかった）
　↓
対応の限界（介入の判断基準がなかった）
　↓
学習の限界（インシデント後も構造的原因を捉えられなかった）
```

### 組織的要因も分析すること

技術的な能力の限界だけでなく、以下の組織的要因も分析する：

```
【組織的要因】

・意思決定プロセスの構造
・部門間の責任分界
・非定常状態における情報共有の仕組み
・現場が「止める権限」を持っていたか（心理的安全性を含む）
```

## 問5：他の事例にも使える教訓は？

### Safety-IIの教訓（必須・1〜2個）

失敗からではなく、
「今まで成功してきたこと」から引き出せる教訓を
1〜2個、最初に記述してください。

```
【教訓○（成功からの学び）】

■ 通常運転で機能していた仕組み・工夫：
■ それが今回機能しなかった境界条件：
■ その境界条件を広げるための設計変更：
■ 適用できる分野：
■ 適用できない条件（反例）：
```

### 失敗からの教訓

```
【教訓○】：〜〜〜

■ 内容：
■ 適用できる分野：
■ 適用条件：
■ 適用できない条件（反例）：
■ 実装の難易度：（技術的／組織的）
■ 成功のための前提条件：
■ よくある失敗パターンとその回避策：
```

### 優先順位マトリクス

各教訓について、以下の表で整理すること：

| 教訓 | 効果 | コスト | 実装期間 | 優先度 |
|------|------|--------|----------|--------|
| 教訓1 | 高/中/低 | 高/中/低 | X-Yヶ月 | 最優先/高/中/低 |

## 付録：用語集

### 基本概念（全分野共通）

| 用語 | 意味 | 例 |
|------|------|-----|
| **Safety-I** | 「何が失敗したか」を起点とする安全管理の考え方。失敗・逸脱の原因を取り除くことを目標とする | ヒヤリハット分析、根本原因分析（RCA） |
| **Safety-II** | 「なぜ普段うまくいっているか」を起点とする安全管理の考え方。成功を支える適応能力を強化することを目標とする | レジリエンスエンジニアリング、Work-as-Done分析 |
| **制御ループ** | 「観測→判断→行動」のサイクル | 温度を測る→高いと判断→冷却する |
| **フィードバック** | 行動の結果が制御者に返ってくる情報 | 冷却後の温度を再測定 |
| **インターロック** | ある条件を満たさないと次の動作ができない仕組み | 扉が閉まらないと機械が動かない |
| **フェイルセーフ** | 故障しても安全側に倒れる設計 | 停電したら信号機は全て赤になる |
| **縮退運転** | 一部機能を制限して安全を確保する | 速度制限運転、出力制限運転 |
| **MOC** | Management of Change。設備・手順・条件の変更を管理するプロセス | 配管切り替え時の影響範囲評価 |

### 分野別用語

#### 🏭 化学プラント・プロセス産業

| 用語 | 意味 | 例 |
|------|------|-----|
| **リリーフ弁（安全弁）** | 圧力が設定値を超えたら自動的に開く弁 | 反応器の過圧防止 |
| **トリップ** | 異常検知時の自動緊急停止 | 高温トリップ、高圧トリップ |
| **DCS** | 分散制御システム | プラント全体を監視・制御するシステム |
| **縁切り** | 修理対象設備をガス・流体から完全に遮断すること | 仕切り板挿入、バルブ閉止 |
| **デッドレッグ** | 流体が滞留しやすい配管の行き止まり部分 | 腐食・固形物堆積の起点 |

#### 🔐 サイバーセキュリティ

| 用語 | 意味 | 例 |
|------|------|-----|
| **多要素認証（MFA）** | 2つ以上の認証要素を組み合わせる認証方式 | パスワード + SMSコード |
| **ゼロトラスト** | 「決して信頼せず、常に検証する」セキュリティモデル | 社内ネットワークでも全てのアクセスを検証 |
| **SIEM** | セキュリティ情報・イベント管理システム | 複数のログを統合分析 |

#### 🏥 医療・ヘルスケア

| 用語 | 意味 | 例 |
|------|------|-----|
| **バイタルサイン** | 生命徴候（体温、血圧、脈拍、呼吸等） | 患者状態の基本的指標 |
| **RRS** | 院内迅速対応システム（Rapid Response System） | 急変の兆候がある患者への早期介入 |
| **EWS** | 早期警告スコア（Early Warning Score） | バイタルサインから患者の状態悪化を予測 |

#### 🚆 運輸・交通

| 用語 | 意味 | 例 |
|------|------|-----|
| **ATS/ATC** | 自動列車停止／制御装置 | 信号超過や速度超過時の自動ブレーキ |
| **デッドマン装置** | 運転士の意識喪失を検知する仕組み | 一定時間操作がないと警報→自動停止 |
| **フールプルーフ** | 人間の誤操作を防ぐ設計 | 2つのボタンを同時に押さないと動作しない |

#### ⚡ 電力・エネルギー

| 用語 | 意味 | 例 |
